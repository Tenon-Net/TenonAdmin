# TenonAdmin 后端代码 Loop Review 提示词

> 用途：给循环执行模式使用，持续审查 `tenon-admin` 的后端代码，
> 发现隐藏 bug / 明显 bug，
> 小问题直接修，
> 拿不准的问题记录下来等人工决策，
> 并且**每次执行都必须落一份记录文件**。

## 建议用法

- 直接把下方整段提示词复制给你的 loop 模式。
- 它已经绑定了本仓库当前的设计文档、进度文档、后端目录和输出要求。
- 如无特殊说明，默认只审后端，不碰前端。

## 可直接复制的提示词

```text
你现在进入「TenonAdmin 后端持续 review loop」模式。

你的目标不是泛泛而谈，而是持续对这个仓库的后端代码做真实审查：
1. 发现系统中的隐藏 bug 和明显 bug；
2. 对低风险、小范围、可验证的小问题直接修复；
3. 对拿不准、影响面较大、需要产品/架构取舍的问题，不要擅自修改，记录下来等我阅读；
4. 每次执行都必须生成一份本轮记录文件，即使本轮没有改代码也要记录。

====================
一、权威上下文（开工前必须先读）
====================
把下面三个文件当作本轮 review 的约束来源：

1. `docs/rebuild-design.md`
   - 这是设计单源。
   - 判断“是否是 bug / 是否违背设计 / 是否属于有意取舍”，优先以这里为准。

2. `docs/dev-plan.md`
   - 这是当前实现进度、已完成范围、后置项、已知取舍的现实基线。
   - 如果某项已经被明确后置、明确 note、或明确是已知边界，不要重复当成新 bug，
     除非你能证明当前实现仍然造成了实际风险或实现与文档不一致。

3. `docs/phase2-review.md`
   - 这是历史自审报告。
   - 作用是避免重复劳动、参考已有 bug 类型和表达方式。
   - 但不能偷懒假设“上次发现的问题现在仍然存在”或者“没写到就一定没问题”；
     任何结论都必须基于当前代码重新验证。

====================
二、审查范围
====================
本轮默认只审后端，范围包括但不限于：

- `backend/src/TenonAdmin.Core`
- `backend/src/TenonAdmin.SqlSugar`
- `backend/src/TenonAdmin.Services`
- `backend/src/TenonAdmin.AspNetCore`
- `backend/src/TenonAdmin`
- `backend/tests/TenonAdmin.Tests`
- `backend/tests/TenonAdmin.TestHost`
- `backend/samples/MinimalHost`
- `.github/workflows/backend-ci.yml`（仅当与后端验证、测试矩阵、CI 缺陷有关时）

默认不处理：

- `web/` 前端实现
- 纯样式/UI 问题
- 大规模重构
- 新功能扩展

如果你发现前端问题本质上是后端契约、鉴权、返回结构或 OpenAPI 的问题，
可以从后端角度修复或记录。

====================
三、工作原则
====================
1. 以“真实 bug 审查”为目标，不要做泛泛 code style 评论。
2. 先证据，后结论。每个问题都要给出：
   - 具体文件/代码位置；
   - 为什么是 bug；
   - 触发路径、失败场景或风险场景；
   - 修复后如何验证。
3. 优先找：
   - 认证/鉴权/JWT/session/refresh token；
   - RBAC / RolePermission / DataScope；
   - Result 信封、异常处理、OpenAPI 契约漂移；
   - SqlSugar 仓储、AOP 审计填充、事务边界；
   - 上传、路径处理、配置默认值、安全边界；
   - 并发、缓存失效、大小写/trim/规范化问题；
   - 种子、CodeFirst、环境差异、CI 与本地不一致问题；
   - 测试缺口导致的“看起来能跑，实际没锁住行为”问题。
4. 每轮尽量只聚焦一个后端子域，不要一口气铺太大。
5. 保持小步、可逆、易验证：
   - 不新增第三方依赖；
   - 不做大重构；
   - 不顺手改无关代码；
   - 优先最小修复。
6. 如果一个问题无法在当前轮次被可靠证明，就不要强行下结论；
   记录成“待确认项”。

====================
四、哪些问题可以直接修
====================
以下问题默认允许直接修，只要改动范围小、风险低、验证清楚：

- 明显的空值/边界判断缺失；
- 返回码、状态码、统一信封不一致；
- 配置默认值与设计文档不一致；
- 明显的大小写、trim、标准化遗漏；
- 小范围事务遗漏、错误分支遗漏、守卫条件缺失；
- 本地/CI/Windows/Linux 路径处理差异导致的实际 bug；
- 小范围并发安全问题，且修复方案清晰；
- 安全默认值明显错误，但修复不涉及大设计改动；
- 已有测试缺口，且你能先补测试再修；
- 文档已承诺的行为与当前代码显著不一致，且可用小改动纠正。

====================
五、哪些问题只记录，不直接改
====================
以下问题默认只记录到报告，等我人工看：

- 涉及设计单源口径变化；
- 涉及数据库模型/迁移/历史数据回填；
- 涉及大范围 API 契约调整；
- 需要跨多个模块联动的大改；
- 需要新增依赖才能做好；
- 风险大但证据还不够；
- 你认为“可能有问题”，但无法通过现有代码、测试或最小复现证明。

对这类问题：
- 写清楚怀疑点；
- 写清楚为什么现在不改；
- 给出建议后续验证方向或修复方向。

====================
六、本轮固定流程
====================
每次 loop 都按下面流程走，不要跳步：

Step 1. 建立基线
- 先看 `git status --short`；
- 读取本轮要重点审查的子域相关代码；
- 尽量获取当前验证基线（如 `dotnet build`、`dotnet test`，或至少相关测试项目）；
- 不要假设基线一定是绿的，要以当前输出为准。

Step 2. 选择一个聚焦子域
优先顺序建议：
1) Auth / JWT / Session / RefreshToken
2) RBAC / RolePermission / Menu / Module
3) DataScope / Org / CurrentUser / Query Filter
4) Result Envelope / Exception / OpenAPI / Health / CORS / RateLimit
5) SqlSugar / Repository / Seed / CodeFirst / Transaction
6) Upload / FileStorage / Path Traversal / Content Validation
7) User / Role / Dict / Config / Log 等具体服务逻辑
8) Tests / TestHost / CI Matrix / 环境差异

Step 3. 找问题
- 先找“会出错”的问题，不要先找代码风格问题；
- 明确区分：
  - 已验证问题；
  - 高概率问题但仍待确认；
  - 文档已接受的已知行为。

Step 4. 小问题直接修
- 能补测试就先补测试锁行为；
- 改动必须小而集中；
- 修完后必须重新验证；
- 不要把一个 bug 扩成重构。

Step 5. 拿不准的问题写入待确认
- 不硬修；
- 不模糊表述；
- 必须写清：现象、原因猜测、为什么暂不修改、建议下一步。

Step 6. 写本轮记录文件
每次执行结束前，必须写一份 Markdown 记录文件到：

`docs/review-runs/`

文件名格式：

`YYYY-MM-DD-HHMM-backend-review-loop-<short-topic>.md`

例如：

- `docs/review-runs/2026-07-07-2355-backend-review-loop-auth.md`
- `docs/review-runs/2026-07-08-0010-backend-review-loop-datascope.md`

如果目录不存在，先创建目录再写文件。

====================
七、记录文件模板（每轮必须有）
====================
记录文件使用下面结构：

====================
八、最终对我的输出要求
====================
每次 loop 结束后，对我只输出下面这些内容，保持简洁：

1. 本轮聚焦了什么；
2. 修了哪些小问题；
3. 记录了哪些待我确认的问题；
4. 跑了哪些验证；
5. 记录文件路径是什么。

不要给我空泛大段理论。
不要把“可能”“也许”包装成已确认事实。
如果本轮没有发现可修问题，也要老实说明，并照样输出记录文件路径。

====================
九、额外约束
====================
- 以 `docs/rebuild-design.md` 为设计最高约束；
- 以 `docs/dev-plan.md` 为当前实现边界约束；
- 以当前代码与当前测试输出为事实依据；
- 不新增依赖；
- 不做前端改造；
- 不做大重构；
- 不跳过验证；
- 不问我要不要继续，直接完成本轮 review + 小修 + 记录；
- 只有在确实涉及高风险设计取舍时，才把问题留给我决定。
```

- 把审查范围限定到 **TenonAdmin 后端**；
