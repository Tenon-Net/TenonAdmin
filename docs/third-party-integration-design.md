# 第三方系统接入模块设计

状态：2026-09-27 经用户整体确认，作为后续实现与验收的设计基线；已实现并通过 G13 完整验收（2026-09-29），证据见[证据记录](third-party-integration-evidence.md)。已确认决策见 [ADR 0008](adr/0008-system-integration-boundary.md)。

实施入口：[Goal 任务拆分与验收计划](third-party-integration-goals.md)。

## 目标与边界

让 TenonAdmin 消费者复用完整的第三方接入机制，仅编写业务接口和第三方适配代码即可完成对接。框架是通用后台框架，ERP、财务等仅为场景示例，不引入对应业务实体或行业规则。

以官方可选模块交付后端默认实现、Vue/React 管理界面、开发模板和可运行示例；无需消息中间件。服务保留接口、可覆写步骤及前置注册优先的替换契约。具体包名和拆分数量按依赖确定。

## 开发者流程

### 向第三方开放接口

1. 安装并显式启用模块。
2. 使用模板定义版本化业务接口、输入输出模型，调用已有业务服务。
3. 声明接口对接入应用开放，显式绑定业务数据范围；确实允许全部数据时也须明确声明。输出模型只包含允许公开的字段。
4. 框架登记规范化路由权限，接入认证、授权、限流、审计和独立 OpenAPI 文档。应用授权与后台用户角色授权分开，权限标识继续遵守 `VERB:/api/...` 约定。
5. 管理员创建接入应用、发放凭据并授权；第三方按文档调用。

开发者不需要自己编写 API Key 校验、应用停用判断、权限中间件、调用日志或通用管理页面。框架不自动推断业务数据归属，不自动暴露所有控制器或数据库表。

### 调用第三方接口

1. 配置目标地址及凭据来源。
2. 编写适配器，处理第三方认证、请求/响应映射及业务错误。
3. 普通查询通过默认调用能力执行，获得超时控制、请求追踪和脱敏调用记录。
4. 对需要可靠送达的操作，在本地业务事务内写入投递记录，由框架后台投递。
5. 适配器声明去重与结果确认能力；结果未知或重试耗尽时，管理员从投递记录进入核对和恢复流程。

入站凭据用于校验，保存摘要；出站凭据用于向第三方认证，必须可取用，不能照搬摘要存储。出站默认由部署配置或秘密提供方供给，管理界面不回显秘密；首版不建设通用密钥托管平台。

## 契约与扩展责任

| 能力 | 框架默认实现 | 消费者扩展责任 |
|---|---|---|
| 应用认证 | HTTPS + 高强度 API Key；到期、撤销、轮换 | 需要时适配企业身份平台 |
| 接口授权 | 接入应用与路由权限绑定，默认拒绝 | 声明可开放的业务接口 |
| 数据范围 | 强制要求显式范围策略，未绑定不放行 | 定义机构、业务归属等过滤条件并覆盖查询及写操作 |
| 返回字段 | 模板要求明确输出模型 | 选择允许公开的字段，不直接序列化实体 |
| API 契约 | 独立版本路由、文档与通用约定 | 维护业务字段和语义兼容性 |
| 出站调用 | HTTP、超时、追踪、脱敏记录、目标地址安全校验 | 第三方认证及协议适配 |
| 可靠投递 | 事务写入、后台领取、重试、状态及人工恢复 | 业务投递时机、去重及结果确认 |

开放接口路由采用 `/api/open/v1/...` 形态。分页、数字业务错误码等优先沿用仓库既有契约；具体字段和类型在实施时核对现有实现，避免产生第二套通用协议。对外时间格式、分页上限、请求追踪规则须在模板与文档中明确。

API Key 不进入 URL 或日志；应用凭据不能调用后台用户管理接口。开放接口不依赖个人登录会话，也不能因缺少用户身份而绕过数据过滤。日志默认记录身份标识、接口、结果、耗时和追踪标识，不默认记录完整业务正文。

入站限流按接入应用生效，未认证请求仍须受基础限流保护。调用记录和投递记录均须有可配置保留策略；清理不得静默删除未解决的投递任务。

### 可靠投递边界

- 同库同事务是本地业务与投递记录原子提交的前提；跨库不承诺原子性。
- 后台领取必须支持多副本并发与进程中断恢复；稳定幂等标识不随尝试次数改变。
- 网络超时不等于远端失败。重试规则结合远端去重、查询确认和业务语义确定，不能仅按 HTTP 状态码一律重发。
- 对方仅返回“已受理”时，不直接标记业务完成；适配器需要区分受理和最终确认。
- 人工重试遵守同样的去重及核对规则，并记录操作者，不能绕过不安全重试限制。
- 不默认保证不同投递之间的顺序，不实现通用双向冲突合并；有顺序要求的业务须明确接入策略。

## 管理界面

Vue 与 React 均提供接入应用创建和停用、凭据创建/到期/撤销/轮换、接口授权、脱敏调用记录，以及投递状态、失败原因和受控恢复入口。管理动作使用现有后台用户权限体系，第三方应用不能管理自身授权。

业务数据范围由消费者通过扩展接入；字段权限首版采用明确输出模型，不提供可视化字段规则设计器。不提供公开开发者注册、计费或可视化集成编排。

## 现有能力复用边界

仓库调查发现现有用户认证与机构数据范围可以提供实现参考，但独立应用身份仍需新增；不能直接将用户会话当作应用会话。现有 HTTP 任务可参考其目标地址安全校验，工作流 Outbox 可参考其领取与恢复机制；后者属于工作流范围，不能据此声称通用投递已经实现，也不要求使用者为了系统集成安装审批工作流。

## 验收标准

1. 示例消费者仅启用模块、编写业务接口并声明数据范围，即可由管理员授权后供第三方调用，无需自写认证和日志基础设施。
2. 缺失、错误、过期、撤销的凭据及已停用应用均无法访问；轮换窗口内允许两把有效凭据，窗口结束旧凭据失效，多副本行为一致。
3. 应用 A 无法调用仅授权给 B 的接口，无法读取或修改其业务范围之外的数据；未配置范围不会退化为全量可见；应用凭据不能访问后台管理接口。
4. 独立 OpenAPI 文档准确描述开放接口、安全要求和响应模型；字段白名单之外的数据及认证秘密不出现在响应或日志中。
5. 普通调用可观察超时和远端错误，写操作不会被基础 HTTP 层无条件重试。
6. 业务事务回滚时不产生投递；业务提交后进程退出，投递记录仍可恢复。多副本运行和领取中断不丢任务。
7. 模拟远端执行成功但响应丢失：支持去重的适配器重试不产生重复业务；无去重或查询能力的适配器进入待核对，不盲目重发。
8. 重试耗尽可查看原因并触发告警；人工恢复保留稳定幂等标识和操作审计。远端异步受理不会误报最终成功。
9. 两套管理界面完成相同管理流程；使用者能前置替换默认服务；未安装或未启用模块时不启动相关后台任务。

验证以针对性集成测试、故障注入、消费者示例及双前端检查为主。本文不表示这些验证已执行。

## 实施顺序建议

先完成开放接口纵向闭环（认证、授权、数据范围、文档、双前端管理与示例），再完成普通出站调用和可靠投递闭环，最后验证替换能力、恢复路径及完整二次开发文档。两条闭环均属于已确认首版范围，不因分步实现而缩减交付。
