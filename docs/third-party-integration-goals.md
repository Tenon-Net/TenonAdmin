# 第三方接入模块：Goal 实施计划

状态：G01–G13 已完成并通过验收，证据见[证据记录](third-party-integration-evidence.md)。本文件不表示已创建或完成运行时 goal。

依据：[已确认设计](third-party-integration-design.md)、[ADR 0008](adr/0008-system-integration-boundary.md)、[领域术语](../CONTEXT.md)。产品范围已确认，日常实现选择由执行者结合代码确定，不需要重新进行需求访谈；改变首版范围或安全保证时才需要回到用户决策。

## 如何执行

推荐使用一个总 goal 连续执行本计划，逐项保留验收证据；不要为每个函数或文件创建 goal。

可直接提交的总目标：

```text
/goal 按 docs/third-party-integration-goals.md 顺序完成 G01–G13，实现已确认的通用第三方接入模块。以 docs/third-party-integration-design.md 和 ADR 0008 为范围基线。逐项目标完成实现、针对性验证并记录证据，再进入下一项；不得用模拟实现代替交付，不缩减双前端、可靠投递、开发模板和完整示例范围。最终通过 G13 的完整验收后才完成总 goal。保留现有无关修改和其他运行时记录，不发布版本或推送代码。
```

也可以只执行一个目标，下面文本中的 `G02` 可替换为任意编号：

```text
/goal 完成 docs/third-party-integration-goals.md 的 G02。先检查并核实其前置目标的交付证据；完成本节任务及共同质量门槛，记录结果后停止，不自动扩大到后续目标。若前置能力缺失，报告具体缺口，不以占位实现绕过。
```

本文件定义任务范围和完成标准，不是 OMX 运行时状态源。执行时若采用 ultragoal，由其受支持命令创建或导入计划、生成实际运行时 ID，并通过生命周期工具维护状态；不要手写 `.omx/ultragoal/` 状态，也不要覆盖其他工作的历史计划。默认使用一个 aggregate goal，以下 G01–G13 是稳定的文档任务编号。

## 共同质量门槛

- 所有实现沿用框架分层、`TryAdd*`、可覆写步骤及 `ApplicationAssemblies` 发现契约；核心层不引入 ASP.NET/SqlSugar 依赖，不额外引入未经授权的新依赖。
- 可选模块默认不启用。未安装/未启用时，不暴露其管理与开放端点、不启动其后台任务、不影响已有登录、数据范围或双前端启动。
- 每个逻辑目标留下能证明行为的针对性测试，尤其覆盖拒绝、越权、事务回滚与恢复；不要用仅验证实现细节的测试替代行为证据。
- 后端变更运行 Release 构建和涉及的测试类；前端变更运行相应模板的 lint、typecheck、build 和必要交互验证。具体测试名称以实际实现为准，不把本计划中的场景描述当作已有测试。
- OpenAPI 变化按仓库规则生成两套 `schema.d.ts`，运行 `node scripts/check-contract-drift.mjs` 并核对输出。该工具可能相对 HEAD 报告本次预期差异，要区分预期契约变动与遗漏，不手改生成文件或覆盖预先存在的修改。
- 数据库敏感行为核对当前 CI 矩阵，保留多副本 smoke 与 SQL Server nightly 覆盖；缺失环境如实记录，关键验收没有证据不能宣称通过。
- 文档与注释使用中文。修改 `site/` 时执行 write-docs 技能，保持中英文事实一致并执行 prose 检查。
- 单项目标只在所有验收项通过时完成。记录修改文件、验证命令与结果、限制及遗留问题；最终目标还须完成清理和独立评审。

## G01 — 模块落点与实现契约

**目标：** 将已确认产品设计落到具体包依赖、现有复用位置和可实现的扩展契约，使后续目标不再自行猜测身份、事务和状态含义。

任务：

1. 使用 CodeGraph 核对认证注册、Controller 发现、数据过滤与写操作、审计填充、OpenAPI、HttpAdminJob、工作流 Outbox 和既有卫星包模式，记录可复用点及限制。
2. 创建 `docs/third-party-integration-implementation.md` 作为唯一实现契约说明，确定最少包拆分、启用方式、类型归属、数据库实体和必要索引；说明开放接口与后台用户认证隔离方式。后续目标引用并随实际落点更新该文档。
3. 明确系统身份的审计表达，不能伪造用户 ID 或因没有用户机构而跳过隔离；确定应用数据范围如何覆盖列表、详情、修改和删除。
4. 明确出站凭据来源、适配器结果分类、同库同事务入口（包括无活动事务时的行为）、投递状态迁移、领取恢复与去重责任；确定停用/撤销在多副本中的生效规则、限流和保留策略默认值，以及异步受理后的最终确认触发方式。

验收与停止条件：上述决策有文件/符号依据，所有后续任务能映射到具体模块；无新增产品范围或未处理的契约冲突。此目标以设计落地文档结束，不生成空壳接口、数据库表或管理页面。

## G02 — 接入应用与凭据生命周期

**目标：** 提供可管理、可撤销的独立接入应用身份及完整 API Key 生命周期。

任务：

1. 建立可选模块注册和应用/凭据持久化，提供创建、停用、到期、撤销及轮换的后台服务与接口；管理接口使用既有用户权限体系。
2. 使用平台加密随机能力生成高强度凭据，采用具有唯一索引的非秘密凭据标识定位记录后校验摘要，避免遍历全部密钥；秘密仅创建时返回。支持有期限的新旧凭据并存，查询接口不回显秘密。
3. 提供默认验证服务及明确系统身份载体；维护多副本停用/撤销的一致行为，不能只清除发起节点的本地缓存。

验收与停止条件：默认验证服务将缺失、错误、过期、已撤销、应用停用凭据全部判为无效并有测试；有效轮换窗口与到期边界有测试；两个宿主对同一应用状态给出一致结果；响应、异常和日志无凭据泄露；前置注册可替换验证服务。完成管理后端，不提前开放未经 G03 保护的业务端点，HTTP 认证拒绝行为在 G03 验收。

## G03 — 开放接口授权与业务数据隔离

**目标：** 消费者声明业务接口和数据范围后，即获得默认拒绝、独立应用授权的完整访问控制。

任务：

1. 接入独立认证路径和开放声明，登记规范化路由权限，提供应用授权管理后端；用户令牌和应用凭据不能相互替代进入另一套权限通道。
2. 实现数据范围接入机制：未绑定拒绝，全量须显式声明，读写均校验；支持消费者按自身业务定义范围。框架保证策略必执行，并对其标准数据访问路径提供约束；消费者自定义查询必须正确使用策略结果，不能承诺自动识别任意 SQL 的业务归属。
3. 保持现有审计字段语义，并记录真实应用身份；复用业务服务时不得利用超管路径绕过授权。后台管理员创建应用、修改授权、撤销凭据等动作进入用户操作审计，与应用调用记录区分。
4. 用最小消费者测试端点证明仅需业务 DTO、服务调用和范围声明即可开放能力。

验收与停止条件：应用 A 无法调用 B 专属接口，也不能通过 ID 直接读写范围外记录；缺失范围策略拒绝；后台管理接口拒绝应用凭据；已存在的用户会话撤销、数据范围和审计测试保持通过。证明本目标可用后停止，不将权限工作留给示例自行补齐。

## G04 — 开放 API 的标准与可观测性

**目标：** 开放接口具备稳定协议、独立文档、限流与脱敏调用记录，形成可被第三方真实调用的后端闭环。

任务：

1. 实现 `/api/open/v1/...` 和独立 OpenAPI 分组，统一既有错误/分页约定、时间格式和追踪标识，明确文档在生产环境的受控获取方式。
2. 按接入应用限流，并保护未认证入口；明确多副本限流语义。记录应用、接口、结果、耗时和追踪标识，不默认记录正文或认证秘密。
3. 提供受用户权限保护的调用记录查询、保留期限和清理机制，避免秘密进入 URL、异常或遥测。
4. 接入 G03 的消费者测试端点，验证独立文档只包含目标开放契约；生成并检查双前端管理 API 类型。

验收与停止条件：文档描述真实认证与输入输出；敏感实体字段未被暴露；错误及分页与契约一致；限流、追踪、脱敏和清理有行为验证；调用记录只向获授权后台用户开放。此时入站后端可以独立演示。

## G05 — Vue 接入应用管理

**目标：** Vue 使用者无需自建接入应用管理页面。

任务：

1. 按 `web/COMPONENTS.md`、`web/DESIGN.md` 实现应用创建/停用、凭据到期/撤销/轮换、接口授权与入站调用记录页面。
2. 对接动态菜单、按钮权限、错误本地化和生成 API 类型；一次性凭据展示不能被持久化到前端存储或普通日志。
3. 验证刷新、深链接、空状态、接口失败和无权限操作，未启用模块不出现不可用菜单。

验收与停止条件：真实后端下完成应用创建→发放凭据→授权→成功调用→查看记录→停用后拒绝的交互闭环，完成轮换流程；Vue 检查通过，未引入 React 依赖。

## G06 — React 接入应用管理

**目标：** React 提供与 G05 相同能力，保持模板独立。

任务：

1. 按 `web-react/COMPONENTS.md` 实现 G05 的全部管理流程及异常状态，使用 Ant Design 6 与稳定 zustand selectors。
2. 对接生成 API 类型、动态菜单、按钮权限和本地化；不从 Vue 导入组件、状态或工具函数。
3. 独立执行真实后端交互闭环，检查凭据展示与未启用行为。

验收与停止条件：G05 的能力与交互验收在 React 同样成立；React lint/typecheck/build 通过；无跨模板共享依赖。不能以 Vue 已验证作为 React 通过的证据。

## G07 — 普通出站调用与第三方适配

**目标：** 消费者只编写第三方协议和业务映射，复用框架的出站调用基础设施。

任务：

1. 提供默认 HTTP 调用、超时/取消、追踪、脱敏记录与凭据来源接入；消费者可替换认证和结果解析。
2. 复用或抽取最小的现有目标地址安全能力，覆盖 DNS 变化及重定向；内部系统地址按显式受信配置放行，不能因支持内网而无条件允许任意目标。
3. 区分认证失败、业务拒绝、网络失败、结果未知与异步受理；基础调用层不擅自重试写操作。
4. 提供受后台权限保护的出站记录查询，禁止响应或日志回显出站秘密。

验收与停止条件：本地可控第三方服务验证成功、超时、取消、错误映射和凭据注入；不安全目标被拒绝；一次写调用不会被底层自动重复；替换适配器无需复制 HTTP 基础代码。此目标不启动可靠投递器。

## G08 — 事务内投递记录

**目标：** 本地业务提交与待投递记录具有同库同事务的原子性。

任务：

1. 实现投递记录与必要索引，定义稳定逻辑投递 ID/幂等标识、目标适配器、业务载荷和状态；不将认证秘密固化进载荷。
2. 提供可在消费者当前业务事务中使用的写入入口，避免隐式另开连接或事务；明确无事务与跨库调用的使用边界。
3. 保证提交后可重启读取、回滚无残留；重复入队的行为与唯一性约束一致。

验收与停止条件：真实数据库测试证明提交同时保留业务和投递、回滚两者都不保留、重启记录仍存在、重复标识按契约处理；消费者示例无需手写投递表。此目标不借助假仓储声称事务原子性。

## G09 — 投递恢复、核对与管理后端

**目标：** 可靠投递支持多副本恢复、有限重试、结果核对和可审计的人工操作。

任务：

1. 实现后台领取、租约/并发控制和中断恢复，复用 G07 外呼；保持领取事务与网络调用边界清晰。过期工作者不得覆盖新领取结果，进程在外呼期间中断须按结果未知处理，不能仅因租约到期就认定可安全重发。
2. 根据适配器去重/查询能力决定重试，所有尝试保持原幂等标识；结果未知但不可安全重试时进入待核对状态。
3. 区分待处理、处理中、异步受理待确认、成功、待核对和重试耗尽等业务含义，具体状态名沿用 G01 决策；受理不得误记成功。
4. 提供有上限的退避重试、状态/尝试记录查询、告警扩展与默认可观察输出、人工核对/恢复接口及操作审计。
5. 提供终态记录保留/清理策略，不静默删除未解决记录；人工恢复遵守自动恢复同样的安全条件。

验收与停止条件：双宿主争抢和进程中断不丢记录；远端成功但响应丢失时，有去重能力不会重复业务，无能力进入核对；异步受理继续等待确认；次数/时间上限生效；人工操作不更换幂等标识、不绕过安全限制。验证外部依赖故障不会篡改本地业务成功状态。

## G10 — Vue 出站调用与投递管理

**目标：** Vue 管理员能定位出站故障并完成受控恢复。

任务：

1. 实现出站调用记录、投递列表/详情、尝试历史和状态筛选，区分受理、成功、结果未知与重试耗尽。
2. 接入受权限控制的核对和恢复操作，显示服务端判定的操作可用性与失败原因；不能在页面自行判定某次重试安全。
3. 对接菜单、生成类型和本地化，不在记录详情暴露秘密。

验收与停止条件：真实后端完成失败定位→核对或允许的恢复→最终结果查询；不可安全重试的记录不能被按钮绕过；Vue 检查通过。

## G11 — React 出站调用与投递管理

**目标：** React 独立实现 G10 的全部管理能力。

任务：

1. 实现出站记录、投递列表/详情、尝试历史及受控操作，状态含义与后端、Vue 一致。
2. 保持模板独立、稳定 selectors 和 Ant Design 6 用法；接入菜单、按钮权限与本地化。
3. 独立验证允许恢复、拒绝恢复和远端受理后未完成的交互。

验收与停止条件：G10 的业务验收在 React 同样通过，React 检查通过；不能省略失败与无权限场景。

## G12 — 消费者示例、开发模板与文档

**目标：** 新使用者能照文档以少量业务代码完成入站和出站对接。

任务：

1. 提供可运行的消费者示例，包含公开 DTO、显式数据范围、普通第三方调用、事务内可靠投递及安全恢复；使用通用示例领域，不引入 ERP 实体。
2. 提供本地可控第三方服务或测试宿主，无商业账号也可演示认证、去重、查询确认、响应丢失和异步受理。
3. 补充已有模板体系中的开发入口或可复制模板，明确哪些代码需要消费者填写；不另建一套通用代码生成平台。
4. 编写启用、凭据轮换、接口版本、范围声明、适配器、事务、部署、保留策略和故障排查文档；按需更新站点并遵守中文母版与英文同步要求。
5. 验证打包内容及消费者引用，不能只在源代码工程引用环境下成功。

验收与停止条件：从干净消费者目录按文档走通三个使用流程；消费者不需要重写认证/日志/投递基础设施，不需要安装工作流包或消息中间件；双前端用法完整；模板、包引用和相关文档检查通过。

## G13 — 完整验收与交付证据

**目标：** 证明整个首版满足已确认设计，修复集成问题后再宣布完成。
