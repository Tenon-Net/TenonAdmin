# 费用报销 AI Decision 真实样本采集与标注规范

状态：采集准备稿。配套文件：[可填写 JSON 模板](./expense-ai-decision-real-sample-template.json)。模板没有真实记录、已确认制度或人工标签；本规范不代表已完成采集、获得数据使用授权或完成真实业务验证。

尚无真实制度或数据时，可先运行[独立的模拟演练](./expense-ai-decision-simulation.md)，其记录始终标记为合成，不填入真实模板。

本轮交付采集格式和标注流程。模型仍仅生成 shadow 建议，不能批准、拒绝、完成 task 或推进 token。

## 先确定适用规则

由业务或财务负责人填写模板的 `batch.policy`：制度引用、版本、生效区间、确认人和确认时间。另存可复核的规则表，逐项列出通过条件、拒绝条件、不确定处理、条件冲突优先级、金额精度与币种口径、类别词表及允许的归一化方式。样本必须适用该制度版本；多个版本分别建批次。

[合成评测 v0](./expense-ai-decision-eval-v0.md) 的三个类别、1000 元上界，以及拒绝优先的规则都是评测假设。`expense-guard-v2` 仍只实现这些假设；未经业务确认，不能把它当作真实公司制度，也不能默认用它生成真实样本标签。即使真实规则恰好相同，也要记录确认依据。

| 角色 | 负责内容 |
| --- | --- |
| 业务负责人 | 确认规则、争议处理方式及样本适用范围 |
| 数据保管人 | 确认使用范围，提取时点快照、脱敏、维护受限映射和分组清单 |
| 标注员 A、B | 在看不到模型结果、彼此标签和后续办理结果的条件下独立标注 |
| 裁决人 | 处理分歧，保留双方原始标签及裁决依据 |
| 评测执行人 | 固定版本、执行隔离的 shadow 评测、报告分母和技术失败 |

同一条的 A、B 应是不同人员；裁决人不兼任该条的 A 或 B。数据保管人与评测执行人可以兼任，但开发人员不得提前浏览 holdout 内容。

## 采样与存放

1. 在查看模型结果前，填写 `batch.sampling`：总体范围、时间窗、抽样方法、预定分层和目标数量。先说明“要代表哪些报销申请”，再取数，不只挑容易通过或历史已通过的单据。
2. 覆盖真实类别和币种写法、金额边界、票据状态、重复报销争议、用途不明、字段缺失、重提和最终未办结等情况。说明文本中的注入或矛盾内容有则保留其语义，不为了凑覆盖将虚构记录混进真实集。
3. 代表性抽样和额外收集的疑难案例在 `samplingStratum` 中区分。报告分别列数；过采样后的总体比例不能直接称为生产发生率。样本不足的分层如实标记，不用合成记录补成“真实样本”。
4. 填写 `batch.dataUse`：数据负责人、允许用途、受控存放位置、保留期限和允许的 Provider 数据处理范围。允许内部研究不等于允许向外部模型发送；本次准备工作不发送任何数据。

真实记录、附件、映射表和完整办理日志存放在组织批准的受控位置，不提交 Git、不放进 issue/PR、聊天、测试日志或公开评测报告。仓库只保存空模板和规范。受控位置在模板中用不含凭证的引用标识，不放带鉴权参数的 URL。

## 脱敏与字段来源

给报销单和证据分配随机、不含业务含义的 `caseId`、`sourceRef`、`evidenceRef`。原单号、发票号等映射由数据保管人单独保管；简单对姓名、手机号或发票号做 SHA-256 不等于脱敏。哈希用于完整性校验，不替代访问控制。

删除或替换姓名、电话、邮箱、身份证号、银行卡号、账户、签名、精确地址、可识别公司或个人的编号、凭证和密钥。附件还要处理文件名、二维码、条形码、OCR 隐藏层、批注和元数据。申请人说明用中性占位符替换标识符，同时保留否定、时间关系、冲突和要求忽略规则等语义。

金额、币种、类别及影响规则判断的时间关系应保留；无法在保护隐私的同时保持决策语义时，标记不适合本轮评测并说明原因，不能悄悄改值。脱敏后由另一人检查，填写 `quality.redaction`；未完成检查的记录不外发。

`snapshot.availableAtUtc` 是模拟 AI 节点作出建议的时点，`capturedAtUtc` 是提取快照的时间。只允许把前一个时点已经可获取的信息放入 `modelInput`。无法还原当时状态的历史单据不能冒充当时可见输入，可保留为“不具备时点快照”的采集记录。

模板的 `modelInput` 初始为空对象。按真实快照填写键和值：缺字段就省略该键，原值为 JSON `null` 才填 `null`，未知状态保留原始未知值。禁止统一补成 `false`、`none`、`valid` 或 `not_indicated`。数字按原始 JSON 数字文本保存，避免 Excel、浮点转换或格式化造成舍入；字符串金额不能偷偷转成数字。类别别名、大小写和空格也不要静默修正；如制度允许归一化，保留原值并记录转换版本。

| 候选输入字段 | 来源和判定要求 |
| --- | --- |
| `amount`、`currency`、`category` | 记录申请系统原字段、类型和原始写法；申请人填写的内容仍是申报值，不因结构化就变成已核实事实 |
| `receiptStatus` | 说明来自人工验真、系统校验还是其他证据；上传了票据不等于 `valid`，不能从“最终通过”倒推验真状态 |
| `amountMatches` | 保留核对来源、计算或人工核对方法；不能从模型解释或申请人自述推导 |
| `purposeClear` | 按确认过的制度和当时可见材料判断；后续补充说明不得回填到较早快照 |
| `duplicateEvidence` | 记录查询范围和查询时点；没有查询结果不能默认等于 `none`，争议未定不能写 `confirmed` |
| `personalConsumption` | 区分已确认、未表明和未知；不能把空值当作排除个人消费的证据 |
| `applicantNote` | 脱敏后保留原意，始终不可信，不能覆盖规则、补充缺失事实或成为指令 |

这九项只是与当前工具对照的候选字段。真实制度需要额外字段时，先版本化输入契约与字段来源，不把额外事实塞进说明或标签。每个候选字段在 `fieldProvenance` 中复制一行：记录 `field`、`availability`、`sourceKind`、证据引用、何时可用及核验方法。缺失、脱敏移除或事后才获知的字段也要记录，但不能进入当时的 `modelInput`。

`availability` 取 `present`、`missing`、`redacted`、`after_snapshot`；`sourceKind` 取 `applicant`、`system`、`human_verification`。`sourceSystem` 和 `sourceField` 记录来源系统的受限标识及原字段名，不填连接地址或凭证。`verifiedBy` 只填受限人员标识，未核验填 `null`。来源记录用于审计，不向模型暴露人员身份、原始数据定位信息或标签。

## 双人盲标与争议处理

数据保管人只向标注员提供制度版本、脱敏时点快照和当时证据的必要来源信息。**不能直接把包含完整标签和办理结果的模板文件发给标注员。** A、B 的工作视图分别生成；隐藏对方标签、所有模型 proposal、confidence、policy 分类及 `humanOutcome`。

每人填写 `label`、适用条款 `ruleIds`、简短理由、证据引用、标注时间，并确认 `modelOutputVisible=false`、`laterOutcomeVisible=false`。其中：

| 标签 | 含义 |
| --- | --- |
| `approve` | 按已确认制度及该时点可见证据，可建议通过；不产生审批动作 |
| `reject` | 按已确认制度及该时点证据，可明确建议拒绝；不产生拒绝动作 |
| `manual` | 制度明确要求人工处理，或规则允许的不确定情形；说明缺什么或冲突在哪里 |

`manual` 是业务标签，**不是标注员意见不一致的占位符**。制度不明确、事实无法追溯或 A/B 分歧未解决时，将 `adjudication.status` 留为 `disputed`，最终标签留 `null`。规则表未确认时整批保持草稿，不能强行打标签。

A/B 一致且依据完整时，记录 `status=agreed`，把共同标签、适用条款、理由和证据引用写入统一的 `annotations.adjudication`，填写 `resolvedAtUtc`，此时 `adjudicatorId` 可为 `null`。不一致时由第三人裁决，在同一对象记录 `status=adjudicated`、最终标签、条款、理由、裁决人和时间，保留原始双方记录。所有可计分记录的唯一最终标签都是 `annotations.adjudication.label`，不能留空或临时挑选 A/B 中一份。已受模型或后续结果影响的标注不能用于盲标一致性统计；安排未暴露的人员重标并保留暴露记录。

模板的 `adjudication.status` 取 `pending`、`agreed`、`disputed`、`adjudicated`。`quality.scoringStatus` 取 `pending`、`eligible`、`excluded`。只有规则适用、时点可还原、`quality.redaction.status=passed`、A/B 盲标完成、最终标签确定的记录才能标记 `eligible`；排除必须写 `exclusionReason`，保留在采集总数与排除清单中。评测运行后不能按模型答错与否重新筛样本。

## 人工办理结果单独记录

`humanOutcome` 由数据保管人从真实办理记录填写，不由被测模型生成。`decision` 取 `approved`、`rejected`、`withdrawn`、`cancelled`、`pending`、`unknown`，未知的其他信息留 `null`。记录决定时间、证据引用、是否补充过材料、是否采用制度例外，以及办理人是否看到模型建议。

办理时点晚于快照或使用了额外证据时，最终决定可以与快照标签不同；保留差异原因，不把后续结果倒灌为当时的输入或标准答案。尚未办结、撤回、取消也不能自动映射成 `manual` 或 `reject`。

离线盲标比较称“与标注不一致”。只有真实办理中确实向办理人展示了建议，并记录接受/推翻及原因、明确可比较时点和统计分母后，才能另行定义人工推翻率；单有历史最终决定仍不够。

## 分组、冻结与独立 holdout

在开发人员浏览样本或调试之前，由数据保管人按 `leakageGroupId` 分组。同一报销单的修改、重提、附件复用、同一重复报销争议链及其关联记录属于同组；关联关系传递闭合。不能只按行随机切分，让同一事实出现在 dev 和 holdout 两边。

填写 `batch.splitPlan` 的分组方法、随机种子、dev 比例、分配负责人和时间；比例由目标总体与可获得组数决定，不在本规范里承诺统计效力。组过少或某分层没有独立 holdout 时如实披露，不为凑比例拆组。每条的 `split` 初始为 `unassigned`，分配后取 `dev` 或 `holdout`。

封存 holdout 的样本、标签和证据访问权限。评测执行人只读取运行所需输入，开发调试只看 dev；数据保管人维护暴露记录。看到 holdout 失败后再修改规则、提取逻辑或提示词，该批仅能作为回归集，后续独立验证需要新保留集。真实新批次与 ER-D-001～008、ER-H-001～052 分开编号，不能把旧合成 holdout 换名复用。

冻结前填写 `batch.freeze`：分组清单、输入、标签各自的内容 SHA-256，以及制度版本、代码提交、提取/脱敏版本、模型标识、system/node 指令摘要和 policy 实现摘要。摘要按实际封存文件字节计算，摘要字段本身存于单独清单，避免自引用。修订必须增加 `batch.datasetVersion`，用 `supersedes` 引用前序数据集及版本，并填写 `changeReason`；首版可将这两个字段留空。保留旧文件，不能覆盖历史批次。`holdoutStatus` 取 `not_frozen`、`sealed`、`exposed`，暴露即更新记录。

## 进入真实 shadow 评测的检查项

- 制度、数据用途、字段来源和时点已确认，受控存储与脱敏复核已完成。
- A/B 标签及裁决已完成，未决或排除记录单独计数；最终办理结果与输入/标签隔离。
- 分组无跨 split 泄漏，holdout 已封存，版本及内容摘要齐全。
- 真实输入适配器已实现并验证：只投影白名单字段，保留类型和数值精度，不传标签、办理结果、人员或数据定位信息。
- 真实制度对应的确定性规则已单独确认；不能直接假定 `expense-guard-v2` 适用。
- handler 仍全部人工兜底；真实 Provider 使用范围明确，生产 HTTP ApiKey 限制保持不变。

当前 `ExpenseAiDecisionEval` 的入口只加载固定的 60 条合成数据，并校验 `synthetic=true`、固定编号和 v0 标签规则；它**尚不支持本模板或真实批次**。本次没有新增导入器、运行真实模型或写入任何生产系统。不要把真实数据覆盖到 `expense-reimbursement-v0.jsonl`，也不要将现有 `--live --split dev` 命令当作真实样本入口。

后续报告先列采集总数、排除数、未决数和实际计分数，再分别报告原始建议与规则后建议。错误建议通过分母为可计分样本中期望 `reject/manual` 的数量；错误建议拒绝分母为期望 `approve/manual` 的数量。技术失败留在相应分母且单列，不能伪装成建议人工；分母为零记为不可计算。人工兜底率、流程推进数、分层结果和时延单独列出，不把模型自报 confidence 当作校准概率。

## 开始填写

将模板复制到受控位置，先填 `batch.policy`、`batch.dataUse` 和 `batch.sampling`，再为每张单复制 `samples[0]`。模板中的 `null` 表示尚未填写的采集元数据，不代表实际输入值；`modelInput` 内缺失与 `null` 的区别按前文保留。

`recordKind=template` 的文件不能计分；确认填入真实来源记录后才改为 `collection`，并将各条 `dataOrigin` 填为 `real`。`quality.redaction.status` 取 `pending`、`passed`、`blocked`，只有另一人复核后才能标记 `passed`。带 `Utc` 的时间使用 UTC ISO 8601 格式；制度生效日期按制度自身时区解释并在规则表写明，`effectiveUntil=null` 可表示没有规定结束日期。

模板中默认的 `pending`、`unassigned`、`not_frozen` 和空标签不能当作完成状态。仓库内模板始终保持空白。

## 本地采集检查

[检查脚本](../../scripts/check_expense_collection.py) 使用 Python 3 标准库，只读一个最多 16 MiB 的采集 JSON，不调用模型、不写输入、不连接生产系统。它拒绝重复 JSON 键和 `NaN/Infinity`，保留高精度 JSON 数字，不做金额业务判断或生成标签。

在仓库根目录运行，路径替换为受控位置中的文件：

```bash
python3 scripts/check_expense_collection.py /受控目录/真实采集.json
```

脚本检查批次必要元数据、案例编号唯一性、同组跨 split 泄漏、排除理由和状态枚举。对声明 `eligible` 的样本，额外检查脱敏通过、双人盲标、统一最终标签、独立裁决、九个候选字段的来源完整性，以及字段可用时点、快照和标注时间顺序。UTC 时间接受 `Z` 或 `+00:00`，不接受无时区时间。

`sampling.strata` 填字符串数组，每条的 `samplingStratum` 必须引用其中一项；`splitPlan.seed` 填整数，`devProportion` 填 0 与 1 之间的 JSON 数字。候选字段仍限于前述九项；新增真实业务字段需要先升级输入契约和检查器，不能偷偷作为额外输入进入本版本。

输出只含固定字段路径、错误码和数量，不回显 caseId、说明、制度内容或其他样本值。退出码 `0` 表示已实现的一致性检查通过，`1` 表示填写或状态问题，`2` 表示读取失败、超过大小限制或 JSON 无效。空模板不是 collection，检查它预期返回 `1`，不会被当成真实就绪数据。

`counts` 单列总数、声明可计分数、待处理数、排除数和争议数。争议数与其他状态可重叠；`eligible` 是原文件声明的数量，只有整体检查通过后才说明这些声明满足已实现的形式条件。合法的 pending/excluded 记录可保留在采集包，不会静默变为可计分记录。

检查不是完整 JSON Schema，也不能确认制度是否真实适用、脱敏是否充分、关联组是否遗漏，或人工是否确实盲标。`sealed/exposed` 仅检查冻结字段和摘要格式，不读取封存文件重算摘要；暴露记录及访问控制仍由数据保管人负责。所有输出固定 `readyForEvaluation=false`：退出 `0` 不代表所有样本已就绪，不授予数据外发、真实评测或审批权限，后续仍需真实适配器与前述检查项。

脚本回归不使用真实记录：

```bash
python3 -m unittest discover -s scripts -p test_expense_collection_test.py
```
