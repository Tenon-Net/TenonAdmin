# Internationalization

The copy is written exactly the way the Vue template writes it: `{name}` placeholders, the same namespace split, the same `ext` overlay. What actually needs changing is react-i18next's defaults, three of which disagree with this copy, so `locales/index.ts` pins each one back. There is also a separate dayjs locale to register, or the date panels under a Chinese UI leak English.

## How it's wired

react-i18next is plugged in through `src/locales/index.ts`:

```ts
export const i18n = i18next.use(initReactI18next)
void i18n.init({
  resources,
  lng: useAppStore.getState().locale,
  fallbackLng: 'en-US',
  nsSeparator: false,
  interpolation: { prefix: '{', suffix: '}', escapeValue: false },
})
```

`initReactI18next` wires the instance into React's hooks (`useTranslation`, `Trans`). The initial `lng` reads the persisted `app.locale` directly, so the very first frame is already last session's language — no flash of Chinese before it jumps to English. When the current language is missing a key, it falls back to the `en-US` named by `fallbackLng`. Miss a key in `zh-CN` and the UI shows the English line from `en-US` instead — no error, no exposed key name.

There are only two built-in copy files, `locales/zh-CN.ts` and `locales/en-US.ts`, each default-exporting one object grouped by namespace. No per-component split, no lazy loading.

`resources` wraps the two dictionaries into i18next's shape, and the `translation` layer in the middle is not optional:

```ts
const resources = {
  'zh-CN': { translation: withExt(zhCN, extMods, 'zh-CN') },
  'en-US': { translation: withExt(enUS, extMods, 'en-US') },
}
```

i18next treats the second level as the namespace. This template uses a single namespace, so all copy hangs under `translation`. Drop that layer and `error`, `common` each become namespaces of their own, leaving the default `translation` namespace empty — `t('error.auth.passwordWrong')` then spits the dotted string back out verbatim, with static checks still green.

### The three defaults that must be overridden

Three of i18next's defaults are incompatible with this repo's copy, and each fails quietly, so they're pinned one by one in `init`:

- `interpolation.prefix/suffix` become the single braces `{` `}`. The copy follows vue-i18n's `{name}` style, while i18next expects `{{name}}` by default. Without the change, `t('workbench.welcome')` renders `你好,{name}` with the braces still showing.
- `escapeValue: false`. i18next HTML-escapes interpolated values by default (it's built for `innerHTML`), but React already escapes, so doing it twice would render `&` and `<` in a username as `&amp;` and `&lt;`. The cost: an interpolated result may only go into a JSX text position, never into `dangerouslySetInnerHTML`.
- `nsSeparator: false`. The default `:` separator splits any key containing a colon at the colon — the left half taken as namespace, the right as key — so the lookup misses. A [permission code](/frontend-react/permission) is exactly this `GET:/api/v1/x` shape, and a backend msgKey may carry a colon too. Turned off, a colon-bearing key resolves whole.

### The consumer's ext seam

The two built-in dictionaries are upstream's territory. Doing business on a fork, keep your own copy out of them and drop it into `locales/ext/<locale>/<module>.ts`, default-exporting that module's keys. `locales/index.ts` pulls the directory in with `import.meta.glob`, deep-merging it into the dictionary under the filename as the top-level namespace — you register nothing. That way your copy never lands in the two files that conflict on every upstream sync.

The deep merge (rather than wholesale overwrite) is required: a backend msgKey is a nested key like `error.dict.typeNotFound`, so a consumer adding one line of copy for their own error code should add only that one leaf key — a shallow merge would drop the whole `error` subtree, siblings and all. This convention matches the Vue template word for word, but each keeps its own copy: the shared-layer direction was overturned, the two templates are self-contained on purpose. For the details, see [the two frontend templates](/guide/frontend-templates) and the README in that directory.

### antd ships its own locale

antd's empty states, pagination, and date components carry their own copy, unrelated to our i18n, and it has to switch alongside — in `App.tsx`:

```tsx
<ConfigProvider theme={themeConfig} locale={locale === 'en-US' ? antdEnUS : antdZhCN}>
```

`antd/locale/zh_CN` and `antd/locale/en_US` drive antd's built-in component copy, and `locale` derives from the same `app.locale`. Skip it and you get a Chinese UI with a stray `No data`. So there are two language states, both watching `app.locale`: one is react-i18next, driving `t()`; the other is antd's `ConfigProvider`, driving its internal components.

## Adding a translation key

The two dictionaries are grouped by functional namespace — `common`, `app`, `user`, `menu`, `dict`, `org`, `role`, `log`, `error`, `recycle`, and so on — the same split as the Vue template. Two real examples:

```ts
// zh-CN.ts
user: { title: '用户管理', account: '账号' },
workbench: { welcome: '你好,{name}' },

// en-US.ts
user: { title: 'Users', account: 'Account' },
workbench: { welcome: 'Hello, {name}' },
```

Steps to add a key:

1. Pick the right namespace (open a new top-level one only for a genuinely new feature).
2. Add it to `zh-CN.ts` and `en-US.ts` at once, under the same dotted path, with matching interpolation placeholders (`{name}`, `{count}`).
3. In a component, `const { t } = useTranslation()` for `t`, then `t('namespace.key')`; outside a component (functions in `utils/`), use the `t` exported from `locales/index.ts`.

Every visible string in a view goes through `t('...')`, with no hardcoded Chinese or English literals. That one is a hard rule.

## Switching language at runtime

Language is a persisted UI preference, held in `stores/app.ts`:

```ts
export type Locale = 'zh-CN' | 'en-US'

locale: 'zh-CN' as Locale,
setLocale: (l) => set({ locale: l }),
```

`useAppStore((s) => s.setLocale)` inside a component, `useAppStore.getState().setLocale('en-US')` outside one — either call updates `app.locale`. The whole store is persisted to `localStorage` through zustand's `persist` under the key `app`, and `locale` is on the persist whitelist, so the language choice survives a refresh.

Change `app.locale` once and both locales flip together, because they both derive from this one source. `locales/index.ts` subscribes to the store at module level:

```ts
useAppStore.subscribe((s, prev) => {
  if (s.locale !== prev.locale) void i18n.changeLanguage(s.locale)
})
```

A change to `app.locale` calls `i18n.changeLanguage`, driving `t()`; the `ConfigProvider locale` in `App.tsx` reads the same `app.locale`, driving antd's built-in copy. So one switch flips both sides within the same render. The subscription lives at module level rather than in some component's `useEffect`, because the i18next instance is itself a module-level singleton and the `t` used outside components has to switch too.

How a backend error code lands as `error.*` copy is not covered here. That mapping is numeric code → `msgKey` → translation key, tied to the response contract; see [Talking to the backend](/frontend-react/api-contract). The `te()` exported from `locales/index.ts` is detailed there too: it blocks keys that point at a subtree, letting the error message fall back to the backend's own text.

## Date panels need a dayjs locale too

The month names, weekday abbreviations, and week-start day inside antd's DatePicker and Calendar panels belong to dayjs, not to antd's locale, so `locales/index.ts` carries one extra line at the top:

```ts
import 'dayjs/locale/zh-cn'
```

`ConfigProvider locale` only switches the chrome — buttons, placeholders and the like — while the panel contents come from antd's picker taking the `'zh_CN'` on the locale object and calling `dayjs().locale('zh-cn').localeData()`. antd itself imports not a single dayjs locale, and dayjs silently falls back to `en` for a locale name it hasn't registered. The symptom of missing this line: under a Chinese UI the buttons and placeholders are Chinese, yet the panel shows `Jan`, `Feb`, with the week starting on Sunday. Two languages on one page, while tsc, lint, and tests all stay green and the console says nothing.

Only the registration is needed, not a global `dayjs.locale()`: the picker calls `.locale(...)` explicitly every time. `en` is built into dayjs, so only `zh-cn` gets added. This layer is antd-specific — the Vue template's Naive UI date components carry their own date locale (`dateZhCN`, `dateEnUS`) and never go through dayjs.
