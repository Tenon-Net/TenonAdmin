# Route D: Docker

Containerized delivery. The repo root's `docker-compose.yml` brings up four services: **MySQL + Redis + backend + Caddy (hosting the SPA and proxying `/api`)**.

```bash
docker compose up -d --build
# frontend at http://localhost:8080   backend debug port at http://127.0.0.1:8081/health/ready (loopback only)
docker compose logs app        # the random super-admin password from first startup (if Seed:AdminPassword isn't set explicitly) is here
```

**Why Caddy instead of nginx by default**: swap the site label `:80` in `web/Caddyfile` for your domain, remove `auto_https off`, and Caddy will **automatically obtain and renew a Let's Encrypt certificate** — saving all the manual TLS work when self-hosting. If you'd still rather use nginx: `web/nginx.conf` is still in the repo (the containerized version of the Route B config) — just switch the run stage in `web/Dockerfile` back to `nginx:alpine`.

> The Caddy in Route B is **installed directly on the host** (you install Caddy on the server yourself); the Caddy in Route D runs **inside a container** (`web/Caddyfile` baked into the image). Both follow the same reverse-proxy approach — pick whichever matches whether you're containerizing.

It runs with **`ASPNETCORE_ENVIRONMENT=Production`** — deliberately: this makes compose double as a live test of the "first production startup" path. The three hard requirements from §0 above (explicit JWT secret, explicit table-creation permission on an empty database, upload root moved out of `wwwroot`) must **all** be satisfied at once, or you get one readable startup error per missing piece. All three are set as environment variables in the compose file — just edit them to your own values.

A few things that will trip you up if not called out:

| Gotcha | Why |
|---|---|
| **Named volumes, not bind mounts** | The image runs as a non-root user. A named volume's first mount carries over ownership from the image directory, so the container can write to it; a bind mount overrides that with the host's ownership, and the app simply can't write to SQLite / the upload directory. |
| **No `HEALTHCHECK` in the image** | The `aspnet` runtime image has neither `curl` nor `wget`, so one would always fail. Health checks are left to the orchestration layer, which probes `/health` (liveness) and `/health/ready` (DB + cache). |
| **`.dockerignore` is a security control** | A dev machine's `data/` directory holds a real `admin.db` and `dev-jwt.key`. Without it, a bare `COPY . .` bakes the **signing key** right into an image layer — push that image anywhere, and anyone can forge a super-admin token. |
| **Change `WorkerId` per replica** | Each instance needs a distinct value in 0–63, or IDs generated in the same millisecond collide. See the next section. |

**For your own host**: the directory generated by `dotnet new tenon-app` already ships with a `Dockerfile` (installs the kernel from NuGet, builds your host); the one at the repo root builds the sample host `MinimalHost` from source for the kernel's own CI — you don't need it.
