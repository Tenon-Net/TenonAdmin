# System Integration Technical Reference

Use this reference when implementing open endpoints, custom data scopes, outbound clients, or reliable delivery adapters. If you are configuring an integration application, credentials, and grants for the first time, complete the [System Integration tutorial](./integration.md) first.

Install `TenonAdmin.Integration`, wire two lines, and your business code shrinks to three things: the DTOs you expose, the other system's protocol, and one enqueue call. Credentials, authorization, data scope, call records, target-address safety, and delivery recovery belong to the framework. When another system calls you, write an open API endpoint. When you call another system, enqueue a reliable delivery if its outcome must commit or roll back with your local business write; otherwise make a plain call. Without the package there are no `itg_*` tables, endpoints, menus, or background jobs, and nothing that already works changes.

The step-by-step checklist for agents lives in the repository at `skills/wire-integration.md`. Two runnable examples exist: the `Integrations/` folder generated by `dotnet new tenon-app --integration`, and `backend/samples/IntegrationSample` in the kernel repository. The latter pairs with the local controllable third party `backend/samples/IntegrationMockPartner`, so deduplication, query confirmation, lost responses, and asynchronous acceptance can all be demonstrated without any commercial account.

## Enable

```bash
dotnet add package TenonAdmin.Integration
```

Wiring takes two steps, like the workflow package, and both are required:

```csharp
using TenonAdmin.Integration;

builder.Services.AddTenonAdminIntegration(builder.Configuration); // options and services, all TryAdd
builder.Services.AddTenonAdmin(builder.Configuration, o =>
{
    o.ApplicationAssemblies.Add(typeof(Program).Assembly);
    o.UseIntegration();                                            // itg_* tables, admin and open endpoints
});
```

Calling `AddTenonAdminIntegration` without `UseIntegration` fails at startup, so background jobs never run against missing tables. If the package is only referenced and neither entry point is called, `[NonController]` makes default controller discovery skip the module controllers, so no endpoints are exposed. Calling only `UseIntegration` includes the `itg_*` entities in table creation but does not register the controller feature provider, menus, or background jobs. Do not use either partial setup; enabling the module requires both entry points.

To replace any built-in service, register the same interface before `AddTenonAdminIntegration`. Enabling the module adds:

- An admin menu "Third-party Integration" with four pages: Integration Apps, Open API Call Logs, Third-party API Call Logs, and Delivery Tasks. Both `web/` and `web-react/` ship these pages; menus and button permissions arrive with the seed, and the menu stays hidden when the module is not enabled.
- Two compiled jobs: `itg-delivery` scans deliveries every 5 seconds, and `itg-retention` purges expired records daily at 03:30. Both obey the scheduler's switch, run log, and alerts.
- A separate authentication scheme, `TenonOpenApp`, used only by open endpoints.

All configuration sits under `TenonAdmin:Integration` and defaults when omitted. Invalid values fail at startup with the offending key in the message.

## Open API: letting others call you

### Write an endpoint

An open endpoint is an ordinary controller with two extra attributes:

```csharp
public sealed record SampleDocDto(long Id, string Title, DateTimeOffset CreatedAt);

[ApiController]
[Route("api/open/v1/sample-docs")]
[OpenApi]
[OpenApiDataScope(OpenApiDataScopes.Org)]
public class SampleDocOpenController(IRepository<SampleDoc> docs) : ControllerBase
{
    [HttpGet]
    public async Task<Result<PagedList<SampleDocDto>>> Page([FromQuery] OpenApiPageInput input) =>
        Result<PagedList<SampleDocDto>>.Ok(await docs.AsQueryable().OrderBy(d => d.Id)
            .ToOpenPagedListAsync(input, d => new SampleDocDto(d.Id, d.Title,
                new DateTimeOffset(d.CreateTime, TimeZoneInfo.Local.GetUtcOffset(d.CreateTime)))));
}
```

Startup checks every open endpoint and refuses to start if any rule is broken:

- The route starts with `api/open/v{n}/`, and every action under `api/open/` carries `[OpenApi]`.
- The HTTP method is explicit, and `[OpenApiDataScope]` names a registered scope policy.
- The return type is `Result<T>`, and `T` contains no persisted entity, directly or through a property.
- No `[RolePermission]`, `[ActiveSession]`, `[RequireReauth]`, or `[AllowAnonymous]`. Open endpoints authenticate only with `TenonOpenApp`, so user tokens cannot reach them and integration credentials cannot reach admin endpoints.

The third rule forces a dedicated DTO for the other side: once audit columns, org IDs, or internal fields appear in an open document, they become a contract you must keep compatible. Paging uses `OpenApiPageInput`, which follows the kernel's `current`/`size` convention with at most 100 items per page. Writes through open endpoints are recorded as inbound calls instead of user operation logs.

### Data scope

Every open endpoint must state how it isolates data. If an app has not bound the scope an endpoint declares, the call is rejected with 403; it never falls back to all data.

| Key | Meaning | What your code does |
|---|---|---|
| `none` | The endpoint reads or writes no scoped data | Nothing; the kernel org dimension is treated as denied |
| `org` | Built-in org scope: bound org IDs, including all descendants | Nothing; queries and by-key updates or deletes on `DataEntity` are enforced by the kernel filter and repository write guard |
| Custom key | Your own business partition, such as a partner code | Write a policy; filter queries with `WhereInScope` and check writes with `EnsureAllowed` |

A custom policy extends `OpenApiDataScopePolicyBase` and supplies the key, the name, and candidate values. If the partition is itself a complete isolation dimension, open up the kernel org dimension explicitly:

```csharp
public sealed class PartnerScopePolicy(ISqlSugarClient db) : OpenApiDataScopePolicyBase
{
    public override string Key => "partner";
    public override string Name => "Ticket partner (sample)";

    public override async Task<IReadOnlyList<OpenApiScopeOption>> ListOptionsAsync(string? keyword, CancellationToken cancellationToken = default) =>
        (await db.Queryable<PartnerTicket>().Select(t => t.PartnerCode).Distinct().Take(200).ToListAsync(cancellationToken))
            .Select(c => new OpenApiScopeOption(c, c)).ToList();

    // The kernel org dimension is denied by default; opening it must be explicit
    protected override DataScopeResult ResolveKernelScope(OpenAppDataScope scope) => DataScopeResult.Unrestricted;
}

// Collection registration; registering the same key twice fails at startup
builder.Services.TryAddEnumerable(ServiceDescriptor.Scoped<IOpenApiDataScopePolicy, PartnerScopePolicy>());
```

Inject `IOpenAppContext` in the controller, filter lists with `query.WhereInScope(app.DataScope, t => t.PartnerCode)`, and check writes with `app.DataScope.EnsureAllowed(input.PartnerCode)`; out-of-scope targets return business code `49004`. The complete example is `PartnerTicketOpenController` in `IntegrationSample`.

`WhereInScope` matches with the database's collation, while `EnsureAllowed` compares the exact value. The default MySQL and SQL Server collations ignore case, so queries treat `ab` and `AB` as the same value but writes do not. Keep scope codes in one letter case, or give such columns a case-sensitive collation.

### Apps, credentials, and grants

All of this happens under "Third-party Integration → Integration Apps":

1. Create an app with a code and a name, plus an optional owner org and per-minute call limit. The owner org anchors rows the app writes; without it, those rows are visible only to unrestricted scopes.
2. Issue a credential. It looks like `tna_<keyId>.<secret>`, and the full value appears only once, in the issue or rotate response. The database stores only a digest, and admin pages and records show only `keyId`. The default lifetime is 365 days, with at most 5 active credentials per app.
3. Under "API & data access", tick open endpoints one by one; anything unticked is denied. Then bind values for the scopes those endpoints use. Permission codes are normalized routes, just like the admin side, such as `GET:/api/open/v1/sample-docs`.

Rotation issues a new credential and expires the old one when the overlap window ends, so both work until the other side switches. Leave the window empty to use the system default (`Credentials:DefaultRotationOverlapHours`, 24 hours by default); the maximum is `Credentials:MaxRotationOverlapHours` (720 hours by default). A window of 0 expires the old credential immediately. Revoking and disabling take effect on every replica at the next request: each open request reads the credential and app state from the database by `keyId`, with no in-process credential cache.

Only a super admin can widen or restore what an app can do: grant endpoints, bind data scopes, issue and rotate credentials, change a credential's expiry, enable an app, or change its owner org. Other admins get `41003` even when they hold those button permissions. This follows the kernel rule that role grants and data scopes are super-admin only: whoever decides how much data a credential can see is effectively a super admin. Stop-loss actions (disable, revoke, delete) and edits to the name, description, and call limit can be delegated through button permissions.

### Calling conventions

The caller sends the credential in the `X-Api-Key` header; it is never read from the URL. An optional `X-Request-Id` is echoed back when valid, and every response carries `X-Trace-Id`, which finds the call in both the inbound call records and the exception log. Responses use the kernel's `{ code, data, ... }` envelope, and failures pair an HTTP status with a business code:

| HTTP | Code | Meaning |
|---|---|---|
| 401 | `49001` | Credential missing, wrong, expired, revoked, or app disabled; the reason is not disclosed |
| 403 | `49002` | The app has not been granted this endpoint |
| 403 | `49003` | The app has not bound the scope this endpoint declares |
| 429 | `49005` | The app exceeded its per-minute call limit |
| 429 | `49006` | Too many authentication failures from one source |
| 400 | `49007` | Invalid request parameters; `args.errors` holds field errors |

Each app gets 600 calls per minute by default (`OpenApi:DefaultRateLimitPerMinute`, overridable per app, 0 for unlimited). Authentication failures are counted per source: well-formed credentials per IP and `keyId`, malformed ones per IP. After more than 30 failures per minute (`OpenApi:AuthFailuresPerMinutePerIp`), requests get 429 before any database lookup. A source that keeps sending a wrong credential therefore cannot lock out other apps behind the same egress address. Behind a reverse proxy, turn on the kernel's forwarded-header settings; otherwise every source counts as the proxy's IP. Without Redis these counters are per replica, so N replicas allow N times the threshold.

Versions live in the route. Within a version, make only compatible changes (new optional fields, new endpoints). Put incompatible changes in a new version by adding `v2` to `OpenApi:Versions`, and keep the old version running until the other side has migrated. Each version has its own OpenAPI document containing only open endpoints. Download it from the Integration Apps page; the underlying admin endpoint `GET /api/v1/integration/catalog/open-api/{version}` requires an admin permission, so production never exposes it anonymously.

The inbound call records store the app, credential `keyId`, endpoint, status code, business code, outcome, failure reason, elapsed time, trace ID, and client IP for every call. Request bodies, response bodies, and headers are never recorded.

## Plain calls: calling a third party

### Configure a target

Each third party is a named target:

```json
"TenonAdmin": {
  "Integration": {
    "Outbound": {
      "Targets": {
        "partner": {
          "BaseUrl": "https://partner.example.com/api/",
          "TimeoutSeconds": 10,
          "TrustedCidrs": [],
          "Auth": { "Type": "Bearer" }
        }
      }
    }
  }
}
```

`Auth.Type` is one of `None`, `Bearer`, `Header` (with `HeaderName`), or `Basic` (with `Username`). Keep the secret out of this file: supply it through the environment variable `TenonAdmin__Integration__Outbound__Targets__partner__Secret`, `dotnet user-secrets`, or a key-vault configuration source. It is read on every call, so a configuration change applies to the next call. If credentials come from somewhere else, register your own `IOutboundCredentialProvider` before `AddTenonAdminIntegration`.

Target addresses are judged by their resolved IPs:

- Loopback, private, and CGNAT addresses are denied by default and allowed only when the resolved address falls inside a range listed in `TrustedCidrs`. List an internal system's range explicitly; supporting internal networks never opens up arbitrary targets.
- Link-local (including cloud metadata), unspecified, multicast, and reserved addresses are always denied, even if listed in `TrustedCidrs`.
- Every connection re-checks the current DNS result. Redirects are not followed and 3xx counts as a rejection, and no system proxy is used. A base URL written as an IP literal is judged at startup.

### Write a client

Extend `OutboundAdapterBase` and write only paths and what results mean:

```csharp
public class PartnerClient(OutboundAdapterServices services) : OutboundAdapterBase(services)
{
    protected override string TargetName => "partner";

    public virtual async Task<PartnerInfo?> FindAsync(string code, CancellationToken cancellationToken = default)
    {
        var response = await GetAsync($"partners/{Uri.EscapeDataString(code)}",
            new OutboundCallOptions { Operation = "partner.get" }, cancellationToken);
        if (response.StatusCode == 404) return null;
        response.EnsureSucceeded(allowAccepted: false); // throws 4903x when incomplete; the frontend localizes by code
        return ReadJson<PartnerInfo>(response);
    }
}

builder.Services.TryAddScoped<PartnerClient>();
```

Paths passed to `GetAsync`, `PostJsonAsync`, `PutJsonAsync`, and `DeleteAsync` are relative to `BaseUrl`; absolute URLs and `../` escapes are rejected. Every call carries `X-Request-Id` set to its call ID. When the other side needs signing or a token exchange, override `AuthenticateAsync` and fetch the secret with `GetCredentialAsync`. When it expresses acceptance or business failure in the response body, override `Classify`.

The framework never retries on its own. Write requests use a fresh connection with `Connection: close`, so the transport will not resend them for you either. Results fall into these outcomes, judged by HTTP status by default:

| Outcome | Default rule | Did the other side execute? |
|---|---|---|
| `Succeeded` | 2xx except 202 | Yes |
| `Accepted` | 202 | It took the request; the final result is pending |
| `AuthenticationFailed` | 401, 403 | No |
| `Rejected` | Other 4xx, 3xx | No |
| `NotSent` | DNS, connect, or TLS failure; blocked target; missing credential; 429 | No |
| `Unknown` | Timeout, dropped connection, 408, all 5xx (including 503 with `Retry-After`) | Possibly |
| `Cancelled` | The caller cancelled | Possibly |

A not-sent result also carries a `Transient` flag. Network failures and rate limits are transient, so a later resend may succeed. A blocked target or a missing or invalid credential is a configuration problem, and resending does not help. Gateways can answer 503 after the upstream has already executed the request. `Retry-After` suggests when to retry; it cannot prove that execution never occurred. All 503 responses therefore count as unknown, while valid retry timing is retained.

`EnsureSucceeded` turns an incomplete result into a business code: target not configured `49030`, not sent `49031`, rejected `49032`, unknown `49033`, accepted `49034` (only with `allowAccepted: false`). The outbound call records store the target, operation, method, URL without its query string, status code, outcome, reason, elapsed time, and call ID. Request headers, request bodies, and response bodies are never recorded.

## Reliable delivery: calls that commit with your business write

A plain call happens outside the transaction, so the local commit and the remote execution are independent. When "if my write committed, the other side will get it" must hold, enqueue inside the business transaction and let the background dispatcher deliver it.

### Enqueue

```csharp
var result = await docs.Db.Ado.UseTranAsync(async () =>
{
    var doc = new SampleDoc { Title = title };
    await docs.InsertAsync(doc);
    await outbox.EnqueueAsync(new DeliveryRequest
    {
        Adapter = SampleDocSyncAdapter.AdapterName,
        Operation = "doc.create",
        DeliveryKey = $"sample-doc:{doc.Id}",     // stable business key; every retry and manual action reuses it as the idempotency key
        BusinessKey = doc.Id.ToString(CultureInfo.InvariantCulture),
        Payload = new SampleDocPayload(doc.Title), // business data only
    }, cancellationToken);
});
if (!result.IsSuccess) throw result.ErrorException;
```

The delivery record and the business row are written to the same database in the same transaction: a commit keeps both, a rollback keeps neither, and a restart does not lose the record. A few rules:

- Enqueue inside an active transaction, or you get `49041`. Set `Standalone = true` only when no business write needs to commit with it.
- Use a stable business key as `DeliveryKey`. Enqueueing the same key with the same content returns the existing record; the same key with a different adapter, operation, or payload returns `49042`.
- Keep secrets out of the payload; the framework fetches credentials on every delivery.
- Make no network calls inside the transaction. Secondary databases do not share the main database's transaction, so enqueue in the same database as the business write.

### Adapters

An adapter extends `DeliveryAdapterBase` and registers by name:

```csharp
public class SampleDocSyncAdapter(OutboundAdapterServices services) : DeliveryAdapterBase(services)
{
    public const string AdapterName = "sample-doc-sync";
    public override string Name => AdapterName;
    protected override string TargetName => "partner";

    public override bool SupportsIdempotency => true; // true only if the other side really deduplicates by idempotency key
    public override bool SupportsQuery => true;       // true if the other side can report a result by idempotency key

    public override async Task<DeliverySendResult> SendAsync(DeliveryContext context, CancellationToken cancellationToken)
    {
        var response = await PostJsonAsync("tickets", context.ReadPayload<SampleDocPayload>(), context.SendOptions, cancellationToken);
        return DeliverySendResult.From(response, ReadJson<PartnerTicketStatus>(response)?.TicketNo);
    }

    // With SupportsQuery = true, implement QueryAsync: map the remote state to Succeeded, Accepted, Failed, or NotFound
}

builder.Services.TryAddEnumerable(ServiceDescriptor.Scoped<IDeliveryAdapter, SampleDocSyncAdapter>());
```

`context.SendOptions` already carries the idempotency key (sent in the target's `IdempotencyHeader`, `Idempotency-Key` by default) and the link to the delivery record. The two capability flags decide what the framework does when a result is unknown, so they must match the other side's real behavior. Declare `SupportsIdempotency` for a partner that does not deduplicate, and a lost response makes the framework resend with the same key and the partner execute twice. When in doubt, leave both `false`.

When an adapter builds a `NotSent` result itself (for example, the other side answers 200 with "try again later" in the body), set `Transient` to `true` so the framework resends with backoff; otherwise the result counts as a configuration problem and the record goes straight to "Exhausted".

The adapter name is stored in delivery records, so drain existing records before renaming it. Names must be 1 to 64 letters, digits, or `._-`, unique ignoring case; otherwise startup fails.

### What the dispatcher does

The background job claims due records, calls the adapter outside any transaction, and writes back with the fence value it claimed. If someone else changed the record after the claim, the write-back does nothing, and a late result is only appended as an attempt. When a result is unknown, the dispatcher branches on the adapter's capabilities, and every resend reuses the same idempotency key:

| Partner capability | When the result is unknown |
|---|---|
| Deduplicates by idempotency key | Resend with backoff |
| Can only be queried | Query first and follow the remote truth |
| Neither | Move to "Needs reconciliation" and alert; never resend automatically |

If the process crashes mid-call and the lease expires, recovery follows the same table; an expired lease alone never counts as proof that a resend is safe. Not-sent results caused by the network or rate limits are resent with backoff: starting at 30 seconds and doubling up to 1 hour, taking a longer `Retry-After` when the other side sends one. After 8 sends or 24 hours since enqueue the record becomes "Exhausted". Configuration problems such as a blocked target or a missing credential are never resent automatically; the record goes straight to "Exhausted" with an alert, and you retry manually after fixing the configuration. Accepted records are polled every 60 seconds when the adapter can query; otherwise they wait for a callback, and after 72 hours without confirmation they move to "Needs reconciliation".

| Status | Meaning |
|---|---|
| Pending | Waiting to be sent or resent |
| Dispatching | The dispatcher is working on it |
| Accepted, awaiting confirmation | The other side took it and the final result is pending; this is not success |
| Succeeded | The other side completed it |
| Needs reconciliation | The result is unknown and a resend is not safe; a person must verify |
| Exhausted | The attempt or time budget ran out |
| Failed | The other side rejected it, or authentication failed |
| Cancelled | Closed manually |

When the other side reports the final result by callback, write an open endpoint that maps its status to success or failure and passes it to `IDeliveryConfirmationService.ConfirmAsync(new DeliveryConfirmation { ... })`. Like any open endpoint, the callback must be granted to specific apps. Three more rules keep one partner from confirming another partner's deliveries:

- `Adapters` is required and lists the adapters this endpoint answers for; deliveries of any other adapter are treated as nonexistent.
- The endpoint declares a business scope (such as `partner`), checks the delivery's business row against the calling app's scope first, and passes that row's business key as `BusinessKey`.
- A delivery that has never been sent does not accept callbacks.

```csharp
[HttpPost("ticket-status")]
public async Task<Result<PartnerTicketCallbackResult>> TicketStatus(PartnerTicketCallback input, CancellationToken cancellationToken)
{
    // The key comes from the other side and cannot be trusted: resolve the ticket and check it against this app's partner scope; invisible means nonexistent
    var ticket = PartnerTicketService.TryParseTicketId(input.DeliveryKey, out var ticketId)
        ? await tickets.Query().Where(t => t.Id == ticketId).WhereInScope(app.DataScope, t => t.PartnerCode).FirstAsync(cancellationToken)
        : null;
    var outcome = ticket is null
        ? DeliveryConfirmOutcome.NotFound
        : await confirmations.ConfirmAsync(new DeliveryConfirmation
        {
            DeliveryKey = input.DeliveryKey,
            Succeeded = input.Status == "done",   // map per the partner's protocol; the full sample rejects unknown statuses
            Adapters = [PartnerTicketSyncAdapter.AdapterName, LegacyTicketSyncAdapter.AdapterName],
            BusinessKey = ticket.Id.ToString(CultureInfo.InvariantCulture),
            RemoteReference = input.TicketNo,
        }, cancellationToken);
    return Result<PartnerTicketCallbackResult>.Ok(new(outcome.ToString()));
}
```

If any rule fails, the result is `NotFound`, which does not reveal whether the record exists. A repeated callback returns `AlreadyApplied`, and a callback contradicting an already confirmed result does not overwrite it. The complete example is `PartnerCallbackOpenController` in `IntegrationSample`.

When a record becomes Needs reconciliation, Exhausted, or Failed, every `IDeliveryAlertSink` receives an alert; the default one writes a Warning log. Add email or chat sinks with `TryAddEnumerable`.

### Manual handling

The Delivery Tasks page filters by status. The detail view shows the payload, a timeline of every attempt, and call IDs that jump to the matching outbound calls. The server computes which actions are available from the status, the adapter's capabilities, and the attempt history; the page only displays them:

- Retry: for failed records, or exhausted records whose current round of sends has no unknown result at a partner that does not deduplicate. It keeps the idempotency key.
- Query the remote result: when the adapter can query.
- Confirm succeeded, confirm not executed: both require a resolution note; after "not executed" the record is sent again under the normal rules.
- Cancel: closes the record; nothing more happens automatically.

Retry, confirm not executed, and a query showing the other side has no such record all start a new round of sends: the attempt budget, the deadline, the confirmation window, and the remote reference start over, and results already handled by a person in an earlier round no longer affect the new one.

Each action sends back the fence value the page saw. If the dispatcher or someone else changed the record meanwhile, the action returns `49046`, so refresh and decide again. An action the status does not allow returns `49045`, even when the API is called directly. Every action records the operator and the note, and lands in the operation log.

## Deployment and retention

- Multiple replicas: credentials and app state are read from the database on every request, so revoking and disabling take effect immediately. Deliveries are claimed by fence, so only one replica wins when several scan at once. Both jobs run on the scheduler's elected leader. Install Redis if the two open API rate counters must be shared across replicas.
- Secrets: outbound secrets come only from configuration sources or your credential provider, never from the database or the payload, and no record, admin endpoint, or log echoes them. The plaintext of an integration credential is returned once, on issue or rotation.
- Proxies: outbound calls bypass the system proxy, because a proxy would defeat the address checks. If traffic must leave through a proxy, restrict reachable targets on the proxy itself.
- `Delivery:LeaseSeconds` (120 by default) must exceed the longest outbound timeout plus the safety margin `Delivery:LeaseSafetyMarginSeconds` (30 seconds by default). Startup checks this, including an options instance you register yourself before `AddTenonAdminIntegration`. When a single call inside a delivery asks for a longer timeout, it is capped at the lease minus the safety margin and a warning is logged, so the call never outlasts its lease.

`itg-retention` purges records daily as follows; 0 days means keep forever:

| Setting | Default | What it purges |
|---|---|---|
| `Retention:InboundLogDays` | 30 | Inbound call records |
| `Retention:OutboundLogDays` | 30 | Outbound call records |
| `Retention:DeliveryDays` | 90 | Succeeded and cancelled deliveries with their attempts, counted from completion |

Pending, dispatching, awaiting-confirmation, needs-reconciliation, exhausted, and failed deliveries are never deleted automatically.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| Startup fails with `TenonAdmin:Integration:...` | Invalid configuration; the message names the key |
| Startup fails with `开放接口声明不合法` | The message lists each offending action; fix it against the four rules in "Write an endpoint" |
| Startup fails with `可靠投递适配器声明不合法` | An adapter name is malformed or duplicated |
| Open call returns 401 `49001` | Wrong, expired, or revoked credential, or a disabled app. The response hides the reason; the inbound call record has it |
| Open call returns 403 `49002` or `49003` | The endpoint is not ticked, or its declared scope is not bound |
| An admin action returns `41003` | Only a super admin can widen what an app can do; see "Apps, credentials, and grants" |
| Startup fails asking for `UseIntegration` | `AddTenonAdminIntegration` was called, but `UseIntegration` was not called in the `AddTenonAdmin` options |
| A callback confirmation returns `NotFound` | The delivery belongs to an adapter the endpoint does not list, its business row is outside the calling app's scope, or it has never been sent |
| Outbound `target_unknown`, code `49030` | The target name is not configured |
| Outbound `target_blocked` | The address was denied: list internal ranges in `TrustedCidrs`; link-local and metadata addresses are never allowed |
| Outbound `credential_missing` | No secret was supplied, so the request was not sent |
| `dns_failed`, `connection_failed`, `tls_failed`, `connect_timeout` | Not sent; safe to resend later |
| `timeout`, `transport_error`, `response_ended` | Unknown; the other side may have executed it, so verify before acting |
| Enqueue returns `49041`, `49042`, or `49043` | No transaction, the same key with different content, or an unregistered adapter |
| A delivery sits in "Needs reconciliation" | The result is unknown and the partner neither deduplicates nor answers queries. Verify in the partner's system, then confirm succeeded or not executed |
| A delivery stays "Accepted, awaiting confirmation" | The other side has not finished. Check `Delivery:ConfirmPollSeconds`, or whether the partner's callback endpoint is granted |
