# Full Container Deployment Walkthrough

This guide uses the `docker-compose.yml` bundled at the repo root to run TenonAdmin fully containerized: MySQL + Redis + backend + frontend, the whole stack with one command. It also doubles as a live test of the "first production startup" path — miss any one of four safety baselines and it refuses to start, with an error naming exactly what's missing.

::: tip Who this compose setup is for
The `Dockerfile` at the repo root builds the sample host `MinimalHost` **from source**, for the kernel's own CI. If you're a NuGet consumer, the directory generated by `dotnet new tenon-app` already includes a `Dockerfile` that installs the kernel from NuGet and builds your own host — use that one instead; the steps below still apply.
:::

## 1. Start the whole stack

```bash
docker compose up -d --build
```

This one command brings up four services (defined in the repo-root `docker-compose.yml`):

- `db` — MySQL 8.0
- `redis` — Redis 7
- `app` — the backend, `ASPNETCORE_ENVIRONMENT=Production`
- `web` — Caddy, serving the frontend's static build and proxying `/api`

Once it's up:

```bash
# Frontend
open http://localhost:8080

# Backend debug port (loopback-only, see "why bind only to 127.0.0.1" below)
curl http://127.0.0.1:8081/health/ready

# The random super-admin password from first startup (when TENON_ADMIN_PASSWORD isn't explicitly set) is here
docker compose logs app
```

## 2. Why it just works by default: four safety baselines are all set as environment variables

Production has a few hard gates — failing them refuses to start rather than running with the risk baked in. The `app` service in `docker-compose.yml` has them all preconfigured; just copy and replace with your own values:

| Environment variable | Config key | Why it must be explicit |
|---|---|---|
| `TenonAdmin__Jwt__SecretKey` | `TenonAdmin:Jwt:SecretKey` | Leaving it unset = dev-key mode (auto-generated, written to disk, with a warning printed). Production must explicitly provide a random string of at least 32 bytes, and it must never go into version control. |
| `TenonAdmin__Database__EnableCodeFirstInProduction` | Same | When `ASPNETCORE_ENVIRONMENT=Production`, even with the table-creation switch on, tables **won't** be created automatically — this is a safety gate preventing the app from `ALTER`-ing a production database on its own. For a first deploy to production with an empty database, this must be explicitly `true` (you can turn it off once tables are created), or have a DBA create the tables manually. |
| `TenonAdmin__Upload__RootPath` | Same | Must be moved out of `wwwroot`. In this compose setup the backend and Caddy are separate, so there's no `UseStaticFiles()` serving the frontend to worry about — but it still needs to be declared as a data volume, or files are lost whenever the container is rebuilt. |
| `TenonAdmin__Id__WorkerId` | Same | Must differ per instance (0–63) when scaling horizontally, or same-millisecond ID issuance collides on primary keys. If Redis is configured (a clear signal of multi-instance intent) but this isn't set explicitly, the kernel **refuses to start outright**, rather than quietly planting a bug that only explodes later. |

Missing any one of these produces a readable startup error in `docker compose logs app` naming exactly which config item is missing — this is deliberate, and much easier to debug than "the process starts fine, then blows up in the driver layer on the first write."

::: warning The values above are demo secrets only
`TENON_JWT_SECRET`, `TENON_DB_PASSWORD`, and `TENON_ADMIN_PASSWORD` in `docker-compose.yml` all have `:-` defaults so you can run it and try it out immediately. **Before deploying for real**, inject real values through the `.env` file in the same directory or your deployment platform's secret management — don't keep the default strings.
:::

## 3. Redis is required for caching, not an optional optimization

`TenonAdmin__Cache__Provider=Redis` on the `app` service in `docker-compose.yml` isn't a performance tweak — it's a **precondition**. A single replica can get by with `Memory` (in-process cache), but the moment you plan to scale horizontally, an in-process cache means: forced logout, permission revocation, and login lockouts on replica A never propagate to replica B — and since the session cache's TTL is the refresh token's lifetime (measured in days), the result isn't "a bit slower," it's these security features **silently failing for days** on the other replica. Switching to Redis routes invalidation through a shared cache keyspace, with zero changes to business code.

## 4. Forwarded headers: letting the kernel see the real client IP

The `app` service also configures:

```yaml
TenonAdmin__Api__ForwardedHeaders__Enabled: "true"
TenonAdmin__Api__ForwardedHeaders__KnownNetworks__0: 172.16.0.0/12
```

Caddy (the `web` service) sits in front; without parsing `X-Forwarded-For`, the backend always sees Caddy's single IP — every user shares one rate-limit bucket (one person brute-forcing login can lock out everyone), and login logs show the proxy's address for every user. **Turning this on requires declaring trusted sources at the same time** (here, the Docker bridge subnet); what's trusted is the "source address," so anyone who can connect directly to the backend port can spoof an IP.

This is exactly why the `app` service's port mapping is written as:

```yaml
ports:
  - "127.0.0.1:${TENON_API_PORT:-8081}:8080"
```

**Bind to `127.0.0.1` only** — binding to `0.0.0.0` would expose "spoof an IP, bypass rate limiting" to the whole LAN; normal traffic all goes through Caddy in front (which already proxies `/api` and `/health`). In production, go a step further and just remove this port mapping entirely, keeping only the reverse-proxy entry point.

## 5. Three easy-to-miss points

| Point | Why |
|---|---|
| **Named volumes, not bind mounts** | The image runs as a non-root user. A named volume inherits ownership from the image directory on first mount, so the container can write to it; a bind mount uses the host's ownership instead, and the app can't write to SQLite or the upload directory at all. `app-data` and `upload-data` in `docker-compose.yml` are both named volumes. |
| **No `HEALTHCHECK` in the image** | The `aspnet` runtime image has neither `curl` nor `wget`, so a health-check instruction would just always fail. Health checking is left to the orchestration layer, probing `/health` (liveness) and `/health/ready` (DB + cache). |
| **`.dockerignore` is a security item** | The repo root has a `.dockerignore` (excluding `data/` and other local directories). A dev machine's `data/` may hold a real `admin.db` and a JWT signing key auto-generated in development — without it, a single `COPY . .` bakes the signing key into an image layer, and once pushed, anyone can forge a super-admin token. |

## 6. Multi-replica deployment (horizontal scaling)

Before starting a second replica, none of the following four points can be skipped — skipping one won't cause an error, it'll just start quietly doing the wrong thing. The repo has a ready-made two-replica overlay, also exercised for real in CI:

```bash
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --build
bash scripts/smoke-multi-replica.sh http://localhost:8080   # verifies each of the guarantees below, one by one
```

`docker-compose.scale.yml` adds an explicit `app2` service (rather than using `docker compose --scale`), because `--scale` can't give each replica its own distinct environment variables, and point ② below specifically requires that:

1. **Redis is a precondition** — see section 3 above; under multiple replicas this isn't optional.
2. **Every replica must have a different `WorkerId`** — `app2` in `docker-compose.scale.yml` explicitly sets `TenonAdmin__Id__WorkerId: "1"`, different from `app`'s `0`. On k8s with a StatefulSet, inject this from the Pod name's ordinal (`app-0`/`app-1`).
3. **The reverse proxy must configure `ForwardedHeaders`** — as in section 4 above, both replicas need this configured, or both will only ever see the load balancer's single IP.
4. **Cold start one replica first** — `app2` has `depends_on: app: condition: service_healthy`, waiting for the first replica to finish writing tables and seed data before starting the second, avoiding a unique-key collision crash from both replicas creating tables at the same time on first boot. On k8s, use an init job / migration job instead.

::: warning The upload directory must be a shared writable volume
`LocalFileStorage` writes to local disk. In compose, both replicas share the same `upload-data` named volume, so there's naturally no issue; but on k8s, if each Pod uses its own PVC, a file uploaded on A returns a 404 on B, and chunked uploads inevitably hit `ChunkMissing`. For multiple replicas, either mount an RWX (ReadWriteMany) shared volume for the upload root, or swap `IFileStorage` for object storage (S3/OSS) up front.
:::

## 7. Post-deployment self-check

```bash
curl https://<your-domain>/health         # Healthy (liveness)
curl https://<your-domain>/health/ready   # Healthy (DB + cache both connected)
curl -i https://<your-domain>/api/v1/ping # 401 = the API route works (this endpoint requires login)
```

Then open the frontend and log in once, confirming you get a menu back — proof that the JWT secret, database, and seed data all line up.

::: tip A 404 on `/openapi/v1.json` in production is expected
It's only mounted in the Development environment as the contract source for `npm run gen:api` on the frontend — it isn't a production endpoint.
:::
