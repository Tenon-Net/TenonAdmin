# 核心概念

开发客户管理、订单管理等业务时，TenonAdmin 提供账号、角色、菜单和权限等通用能力。客户字段、订单规则和业务页面仍由你的项目负责。先分清这两部分，才能判断一项需求应该写在业务代码里，还是通过扩展接口调整框架。

## 为什么不是又一个后台模板

后端通过 NuGet 包接入你的 ASP.NET Core 项目。文档中说的「内核」就是这些通用后端功能；「宿主」是启动它们的应用项目；「业务程序集」则是编译后包含业务实体、服务或控制器的代码模块。

前端以源代码模板交付。选择 Vue 或 React 中的一套，在它的基础上添加页面即可，两套无需同时安装。后端升级通过 NuGet 完成，前端更新需要合并或迁移上游改动。

例如，开发客户管理时，框架负责用户登录和权限检查，你编写客户实体、查询接口和列表页。把业务实体与控制器所在程序集加入 `ApplicationAssemblies`，框架才能发现它们。完整操作见[添加业务模块](/zh/guide/business-module)。

## 用户、角色与数据权限

角色权限决定用户能执行什么操作，数据权限决定他能访问哪些记录。两者需要分别配置。

| 业务问题 | 对应概念 | 客户管理示例 |
|---|---|---|
| 谁在使用系统？ | 用户 | 销售员工的登录账号 |
| 可以访问哪个页面、执行什么操作？ | 角色、菜单与接口权限 | 可以打开客户列表，但不能删除客户 |
| 可以看到哪些记录？ | 角色的数据范围 | 仅本人、本机构、本机构及下级、指定机构或全部 |
| 一条记录属于哪里？ | 创建机构与创建人 | 框架在创建记录时填写相应审计字段 |

RBAC 指「基于角色的访问控制」：给角色授权，再把角色分配给用户。例如，销售主管和销售员工可以访问同一个客户列表，但拥有不同的数据范围。

菜单和按钮决定界面入口是否可见，后端接口仍会独立检查权限。隐藏按钮不能代替后端鉴权。开发时也要用普通用户验证，超级管理员会绕过角色权限检查。

## 请求流水线

用户打开客户列表后，一次请求会经过以下检查：

1. **确认身份**：前端携带登录得到的访问令牌。后端验证令牌和会话；无效身份返回 `401`。
2. **检查操作权限**：标记 `[RolePermission]` 的接口使用规范化路由作为权限码，例如 `GET:/api/v1/sample/doc`。管理员在角色管理中授予对应权限。
3. **确定数据范围**：框架合并当前用户各角色允许访问的数据，写入 `IDataScopeContext`。支持数据范围的查询据此过滤记录。
4. **返回结果**：通常以 `Result<T>` 统一返回数据与状态。业务错误通过数字 `ErrorCode` 标识，前端负责本地化显示；文件下载等响应有自己的格式。

详细流程与扩展点见[请求管线](/zh/backend/request-pipeline)。

## 数据层约定

实体是映射到数据库表的 C# 类型。无需按机构隔离的表通常继承 `BaseEntity`；需要数据范围的表继承 `DataEntity`。框架通过 `SqlSugarScope` 访问数据库，并在支持的查询中应用软删除和数据范围过滤。

创建和更新记录时，框架自动填写 `Id`、`CreateTime`、`CreateUserId`、`CreateOrgId`、`UpdateTime`、`UpdateUserId` 等字段。业务代码填写客户名称等业务字段即可。软删除表示将记录标记为已删除，普通查询会排除这些记录。

查询过滤不等于任意写操作都安全。使用框架仓储的受保护写路径，并在修改或删除前检查记录可见性；原生 SQL 和直接 ORM 写入需要自行落实权限检查。具体边界见[多组织数据权限](/zh/backend/data-scope)。

记录 ID 使用雪花发号器生成。多个实例的 `WorkerId` 必须互不冲突，自动分配与显式配置的规则见[多副本部署](/zh/guide/deployment/docker)。

## 可替换性模型

默认实现不满足业务需要时，可以选择对应的扩展方式：

| 需求 | 做法 |
|---|---|
| 文件改存对象存储 | 实现对应存储接口，替换默认服务 |
| 登录成功后补充处理 | 继承内置服务，覆写对应的 `virtual` 方法 |
| 添加自己的实体与接口 | 注册业务服务，并通过 `ApplicationAssemblies` 登记程序集 |

内置服务使用 `TryAdd*` 注册：同接口已有注册时，就保留已有实现。因此，替换默认服务应在 `AddTenonAdmin()` 之前完成注册。接口、可覆写方法和程序集发现由 `ReplaceabilityTests` 保护，但升级时仍需核对扩展点的兼容性。示例见[替换内置服务](/zh/guide/replace-service)。

## 包分层

一般应用安装 `TenonAdmin` 即可，无需逐个选择底层包。排查依赖或开发扩展时，再按下表定位：

| 包 | 负责什么 |
|---|---|
| `TenonAdmin.Core` | 接口、配置、结果与错误码，不依赖 SqlSugar 或 ASP.NET |
| `TenonAdmin.SqlSugar` | 数据访问、实体基类、自动建表与种子数据 |
| `TenonAdmin.Services` | 内置业务实体、服务、角色权限与数据范围 |
| `TenonAdmin.AspNetCore` | 服务注册、认证、控制器与请求过滤器 |
| `TenonAdmin` | 引用宿主集成层的入口包，安装时带入所需依赖 |

依赖关系是 `AspNetCore → Services → SqlSugar → Core`。分层细节见[架构与包依赖](/zh/backend/architecture)。

需要对接 ERP、仓储或合作方系统时，使用[系统集成](/zh/guide/integration)可选包，为每个外部应用配置独立凭据与接口授权。它与员工登录分开管理；需要可靠发送时，还可跟踪发送任务、重试与人工核对结果。
