# 系统集成：从应用凭据到可靠投递

当 ERP、仓储系统或合作方平台需要调用你的业务接口时，你需要先回答四个问题：谁在调用、能调用什么、能看到哪些数据、失败后如何追踪。`TenonAdmin.Integration` 把这些能力放进同一个模块，并为反向调用第三方系统提供出站记录和可靠投递。

这一页以一个闭环为主线：创建一个合作方应用，发放凭据，只授权必要的接口和数据范围，用独立 OpenAPI 文档完成联调，再观察一条发送任务直到结束。

如果你正在实现开放端点、自定义数据范围、出站客户端或投递适配器，请配合[系统集成技术参考](./integration-reference.md)使用。

## 先判断你需要哪一种能力

下面四个概念解决的问题不同。先分清它们，可以避免把人员权限或后台菜单误配给机器凭据。

| 能力 | 代表谁 | 用在什么地方 |
| --- | --- | --- |
| 集成应用 | ERP、仓储、合作方服务等机器身份 | 调用开放 API，按端点和数据范围授权 |
| 门户应用 | 后台中的一个业务入口 | 组织导航、菜单和页面，不签发机器凭据 |
| SSO | 一名登录后台的人员 | 统一人员身份和登录过程 |
| 工作流 | 一项业务审批 | 编排审批节点、处理人和流转条件 |

本教程使用集成应用。它不会继承后台用户的角色，也不会因为门户中出现了某个菜单就自动获得对应接口权限。

::: info 版本说明
请使用包含系统集成模块的 TenonAdmin 配套版本，并让 `TenonAdmin.Integration` 与 `TenonAdmin` 保持相同版本。元包不会自动引入或启用系统集成模块。
:::

## 第一步：安装并启用模块

新项目可以直接运行 `dotnet new tenon-app --integration -n PartnerAdmin`。模板会引用 `TenonAdmin.Integration`、完成下面两步接线，并生成包含开放接口、普通出站调用和可靠投递示例的 `Integrations/` 目录。

在消费方项目中安装可选包：

```bash
dotnet add package TenonAdmin.Integration
```

然后完成服务注册和程序集登记：

```csharp
using TenonAdmin.AspNetCore;
using TenonAdmin.Integration;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddTenonAdminIntegration(builder.Configuration);
builder.Services.AddTenonAdmin(builder.Configuration, options =>
{
    options.UseIntegration();
});

var app = builder.Build();
app.MapTenonAdmin();
app.Run();
```

`AddTenonAdminIntegration()` 注册选项、认证方案和可替换服务。`UseIntegration()` 必须写在 `AddTenonAdmin` 的配置回调中，它会让模块实体参与建表，并挂载管理端与开放端控制器。漏掉第二步时，宿主会在启动阶段拒绝运行，避免任务已经启动而所需表和端点尚未接入。

如果你要替换模块内置服务，请在 `AddTenonAdminIntegration()` 之前注册自己的实现。模块沿用 TenonAdmin 的 `TryAdd*` 约定，先注册的消费方实现优先。

安装模块只会提供接入基础设施，不会凭空生成你的业务开放接口或发送任务。如果项目中还没有标记为开放接口的业务控制器，授权目录就是空的；如果业务代码没有通过 `IDeliveryOutbox` 入队，发送任务列表也不会出现记录。

要完整走通后续步骤，可以使用 [`IntegrationSample`](https://github.com/Tenon-Net/TenonAdmin/tree/main/backend/samples/IntegrationSample)。它包含工单开放接口、自定义数据范围、出站客户端和两种投递适配器，并配有本地可控的 [`IntegrationMockPartner`](https://github.com/Tenon-Net/TenonAdmin/tree/main/backend/samples/IntegrationMockPartner)。使用包含这两个示例的配套源码，在仓库根目录打开三个终端：

```bash
# 终端 1：本地合作方，固定监听 http://127.0.0.1:5300
dotnet run --no-launch-profile --project backend/samples/IntegrationMockPartner

# 终端 2：示例宿主，固定监听 http://localhost:5100
ASPNETCORE_URLS=http://localhost:5100 \
TenonAdmin__Integration__Outbound__Targets__partner__Secret=partner-secret \
  dotnet run --no-launch-profile --project backend/samples/IntegrationSample

# 终端 3：Vue 管理后台，监听 http://localhost:5175
npm --prefix web install
npm --prefix web run dev
```

`partner-secret` 只是本地 Mock 的固定演示值。首次启动示例宿主后，使用控制台打印的超级管理员密码登录。示例会让开放端点出现在授权目录中；调用后台的 `POST /api/v1/sample/partner-ticket` 创建工单后，才会产生可观察的发送任务。已有业务实现的项目可以跳过示例，直接从下一步开始。

## 第二步：创建集成应用

登录后台，进入 **第三方接入 → 接入应用**，点击“新增”。建议先为一个真实调用方创建一个应用，不要让多个合作方共用同一身份。

填写时重点关注四项：

1. **应用编码**：使用稳定且能识别调用方的编码，例如 `partner-warehouse`。上线后不要把同一编码改作其他系统使用。
2. **应用名称**：写成运维人员能理解的名称，例如“华东仓储接口”。
3. **归属机构**：需要按机构隔离数据时选择。它是应用写入数据时的机构锚点，不等同于后台用户的数据权限。
4. **调用上限**：按合作方容量设置每分钟限额。`0` 表示不限，应经过明确评估再使用。

[![接入应用列表，展示应用编码、调用上限、有效凭据、状态以及凭据和更多操作入口](/screenshots/integration-apps.png)](/screenshots/integration-apps.png)

截图中，“凭据”用于管理 API Key，“更多”用于进入接口和数据权限等操作；表格上方的“下载接口文档（JSON）”会在联调步骤使用。

## 第三步：发放并保存凭据

在目标应用行点击“凭据”，选择发放凭据。完整凭据形如 `tna_<key-id>.<secret>`，只会在创建或轮换成功时显示一次。数据库和后续列表只保存或展示可识别部分，无法替你找回明文。

看到明文后立即完成三件事：

1. 保存到调用方的密钥管理系统或受控环境变量中。
2. 记录负责人、用途和到期时间，避免出现无人维护的长期凭据。
3. 关闭弹窗前确认调用方已经安全接收；不要把真实值放进截图、工单、聊天记录或代码仓库。

需要换钥时使用“轮换”。系统会签发新凭据，并允许旧凭据在设定的并存窗口内继续工作。确认调用方已经切换后，再撤销旧凭据。怀疑泄露时直接撤销，不要等待到期。

发放、轮换或延长凭据会扩大或延续应用的访问能力，因此只有超级管理员可以执行。普通管理员即使拥有对应按钮权限，也会收到 `41003`；撤销凭据属于止损操作，可以按按钮权限委派。

## 第四步：授予端点和数据范围

凭据本身只证明“它属于哪个应用”，不会自动获得业务能力。进入应用的“接口与数据权限”，按最小权限完成两层授权：

1. **端点授权**：只勾选调用方确实需要的开放端点。权限以规范化路由表示，例如 `GET:/api/open/v1/orders`。
2. **数据范围**：为端点声明的范围绑定允许值。没有绑定所需范围时，请求会被拒绝，不会退化为查看全部数据。

| 范围 | 适合场景 | 授权方式 |
| --- | --- | --- |
| `none` | 端点不访问受范围约束的数据 | 不选择业务范围值 |
| `org` | 按组织机构和下级机构隔离 | 选择允许访问的机构 |
| 自定义范围 | 按合作方编码、租户或仓库隔离 | 由业务范围策略提供候选值 |

把“能登录后台”“能看到门户菜单”或“拥有某个人员角色”当作集成授权，都会造成错误配置。集成应用只认自己的端点授权、数据范围、启用状态和凭据状态。

授予端点、绑定数据范围、启用应用或修改归属机构都会扩大或恢复访问能力，只允许超级管理员操作。拥有相应查询权限的普通管理员可以查看已有配置，但不能凭按钮权限扩大应用授权。

## 第五步：使用独立 OpenAPI 文档联调

回到“接入应用”列表，点击“下载接口文档（JSON）”。该文档只包含开放端点，可导入常用 API 调试工具或用于生成客户端。生产环境通过这个受后台权限保护的入口获取文档；不要为了联调把开放端点改成匿名访问。

在调试工具中把凭据放进本地环境变量，并通过 `X-Api-Key` 请求头发送。示例或共享集合中只保留明显占位值，例如 `tna_<key-id>.<secret>`。按下面顺序验证，比一开始只测成功请求更容易发现授权错误：

1. 调用已授权且已绑定范围的端点，确认返回正常业务信封。
2. 调用一个未授权端点，确认返回 HTTP 403 和业务码 `49002`。
3. 移除一个必需的数据范围后重试，确认返回 HTTP 403 和业务码 `49003`。
4. 撤销测试凭据，确认后续请求返回 HTTP 401 和业务码 `49001`。

完成验证后重新签发正式凭据，并只在目标环境的密钥系统中保存。

## 第六步：配置可靠投递

当你的系统需要主动调用第三方时，先在 `TenonAdmin:Integration:Outbound:Targets` 中定义命名目标。下面的配置不含秘密，可以提交到仓库：

```json
{
  "TenonAdmin": {
    "Integration": {
      "Outbound": {
        "Targets": {
          "partner": {
            "BaseUrl": "https://partner.example.com/api/",
            "TimeoutSeconds": 10,
            "TrustedCidrs": [],
            "Auth": {
              "Type": "Bearer"
            }
          }
        }
      }
    }
  }
}
```

把秘密通过 `TenonAdmin__Integration__Outbound__Targets__partner__Secret` 环境变量、用户机密或密钥管理配置源注入。不要把 `Secret` 写进提交到仓库的配置文件。内部地址默认拒绝；确实需要访问内网目标时，只把明确的网段加入 `TrustedCidrs`。链路本地地址和云元数据地址始终不会放行。

可靠投递还需要业务代码完成三件事：为对方协议实现一个 `IDeliveryAdapter`，把它注册进容器，并在业务事务中通过 `IDeliveryOutbox` 入队。适配器必须如实声明对方是否支持幂等去重和按标识查询；框架会据此决定结果未知时能否自动重发。配套源码中的 `backend/samples/IntegrationSample` 展示了完整接法。

入队载荷只放业务数据。凭据在每次发送时读取，不能进入载荷、投递标识或业务键。框架保证每次尝试沿用同一个投递标识，但“只执行一次”仍取决于对方是否真正按该标识去重。

## 第七步：观察发送任务

进入 **第三方接入 → 发送任务**。先按投递标识、适配器、业务操作或业务键搜索，再结合状态标签判断下一步。

[![发送任务列表，展示投递标识、适配器、业务操作、业务键、状态、发送次数和下次处理时间](/screenshots/delivery-tasks.png)](/screenshots/delivery-tasks.png)

截图中同一页同时出现了“成功”“待核对”“失败”和“已受理待确认”，说明它们代表不同结论：

| 状态 | 你该怎么理解 |
| --- | --- |
| 待处理 / 处理中 | 正在等待扫描或已经被投递器领取 |
| 已受理待确认 | 对方接收了请求，但还没有给出最终结果，不能当作成功 |
| 成功 | 对方已经明确完成 |
| 待核对 | 结果未知，而且当前条件下不能安全自动重发，需要人工向对方核实 |
| 重试耗尽 / 失败 | 自动预算已用完，或对方明确拒绝、认证失败，需要先修复原因 |
| 已取消 | 管理员主动结束了任务 |

点击“详情”可以查看尝试历史、调用标识和当前允许的操作。人工重试、确认成功、确认未执行或取消都由服务端再次检查状态，并保留原投递标识。确认类操作要写清依据，方便后续审计。

## 第八步：查看调用记录

模块把两个方向的调用分开记录：

- **开放接口调用记录**：第三方调用你的系统。重点查看应用、凭据标识、端点、HTTP 状态、业务码、耗时、来源 IP 和追踪标识。
- **第三方接口调用记录**：你的系统调用第三方。重点查看目标、业务操作、方法、状态、结果分类、失败原因、耗时和调用标识。

排障时先从发送任务详情取得调用标识，再到第三方接口调用记录查同一次请求；处理开放接口问题时，用响应中的追踪标识关联调用记录和服务端日志。

调用记录不会保存认证头、请求体或响应体，也不应在错误摘要中写入凭据和敏感业务数据。如果业务排障确实需要更多上下文，应记录不可逆摘要或业务侧引用，而不是复制秘密和完整报文。

## 第九步：完成验证并处理常见故障

一个接入闭环至少应通过以下检查：

- 宿主能启动，并能看到“第三方接入”菜单。
- 测试应用只有一组明确用途的端点和数据范围。
- 凭据保存在密钥系统中，仓库、截图和日志中没有明文。
- 独立 OpenAPI 文档可以导入，成功、越权和撤销场景都符合预期。
- 一条测试业务能够生成发送任务，详情中能看到尝试历史。
- 任务与两类调用记录可以通过投递标识、调用标识或追踪标识关联。

| 现象 | 优先检查 |
| --- | --- |
| 启动提示缺少 `UseIntegration()` | 是否在 `AddTenonAdmin` 的配置回调中调用了 `options.UseIntegration()` |
| 开放接口返回 401 / `49001` | 凭据是否完整、过期或已撤销，应用是否停用 |
| 开放接口返回 403 / `49002` | 当前规范化路由是否已授予应用 |
| 开放接口返回 403 / `49003` | 端点声明的数据范围是否已经绑定 |
| 开放接口返回 429 | 应用调用上限或来源认证失败次数是否超限 |
| 出站结果为 `target_blocked` | 目标解析后的地址是否被安全边界拒绝，内网网段是否准确加入 `TrustedCidrs` |
| 出站结果为 `credential_missing` | 密钥配置源能否提供对应目标的秘密 |
| 长时间停在“已受理待确认” | 对方是否支持状态查询，或回调端点是否已授权并正常调用 |
| 任务进入“待核对” | 先向对方确认是否执行，再按详情页允许的操作处理；不要直接创建新任务规避核对 |
